# Пункт (г) - Ограничения унаследованного ландшафта

**Фича:** Управление возвратами  
**Связь:** занятие 5 (ограничения legacy), занятие 10 (публичный интерфейс)

---

## Архитектурные ограничения, которые сделали бы решение недостижимым

**Принцип задания:** Назвать конкретное ограничение из разобранных на занятии 5, а не «легаси мешает"

### Ограничение 1: Публичный программный интерфейс как бессрочное обязательство

**Суть ограничения (занятие 5, занятие 10):**

Публичный API - это контракт с внешними интеграторами, который нельзя сломать без предупреждения. Изменение пути, обязательности поля или смысла ответа ломает работу клиентов-интеграторов (маркетплейсов, ИМ), которые уже используют этот API

**Как это сделало бы решение недостижимым:**

Предположим, что в существующем публичном API есть метод `POST /shipments` (создание отправления), и команда решает добавить возвраты туда же: `POST /shipments?type=return`. Это кажется логичным - «возврат - это тоже отправление"

**Проблема:**

1. Возврат - не подвид отправления, а самостоятельная сущность со связью (пункт 0). У возврата другой жизненный цикл, другие поля (причина возврата, связь с прямым отправлением по ШПИ)

2. Добавление параметра `type` в существующий метод меняет его семантику. Клиенты, которые не передают этот параметр, ожидают создания прямого отправления. Если логика ветвится внутри одного метода, ошибка в одной ветке влияет на другую

3. Через полгода команда понимает, что метод перегружен, и хочет выделить возвраты в отдельный путь `POST /returns`. Но старый путь `POST /shipments?type=return` уже используется интеграторами - нельзя его удалить без мигра ции, которая занимает месяцы (занятие 10: версионирование)

**Обход:**

**Сразу выделить возвраты в отдельный ресурс:** `POST /returns`, `GET /returns/{id}`, `GET /returns`. Это новый контракт, который не влияет на существующий `/shipments`. Если через год потребуется изменить модель возвратов - меняем только `/returns`, а `/shipments` остаётся нетронутым

**Принцип:** Не перегружайте существующий публичный контракт новыми функциями, если они имеют собственный жизненный цикл. Новая сущность - новый ресурс

### Ограничение 2: Каждый сервис со своей базой данных

**Суть ограничения (занятие 5):**

Микросервисная архитектура предписывает: каждый сервис владеет своей базой данных, другие сервисы не имеют прямого доступа к ней. Это изоляция: изменение схемы одной базы не ломает другие сервисы

**Как это сделало бы решение недостижимым:**

Предположим, что команда решает не создавать новый сервис возвратов, а добавить таблицу `returns` в существующую БД сервиса отправлений. Логика: «возврат связан с отправлением, логично хранить их рядом"

**Проблема:**

1. **Граница ответственности размывается.** Сервис отправлений отвечает за жизненный цикл прямых отправлений. Если добавить туда возвраты - кто владелец модели возвратов? Команда сервиса отправлений или другая? При изменении схемы `returns` они будут конфликтовать

2. **Нельзя изменить схему таблицы `returns` без риска повлиять на `shipments`.** Обе таблицы в одной базе под управлением одного сервиса. Миграция схемы `returns` может заблокировать `shipments` (например, долгий ALTER TABLE в Postgres)

3. **Отказ сервиса отправлений убивает возвраты.** Если сервис отправлений падает или перегружен, возвраты недоступны, хотя они не должны зависеть от отправлений (после создания возврат живёт своей жизнью)

**Обход:**

**Выделить сервис возвратов с собственной БД** (пункт 0). Это даёт:

- **Изоляцию:** Отказ сервиса отправлений не влияет на возвраты. Перегрузка возвратов не влияет на отправления
- **Независимость развития:** Команды меняют схемы своих баз независимо
- **Профиль нагрузки:** Возвраты создаются на порядок реже, чем отправления (ЛР-1). Разделение баз позволяет оптимизировать их по-разному (например, реплики для отправлений, но не для возвратов)

**Принцип:** Если у сущности свой жизненный цикл и свой профиль нагрузки, она требует своего сервиса и своей базы

### Ограничение 3: Невозможность распределённой транзакции между базами

**Суть ограничения (занятие 7):**

Когда операция затрагивает две базы данных разных сервисов, невозможно обеспечить атомарность средствами СУБД. Либо всё, либо ничего - эта гарантия теряется. Между двумя подтверждениями существует момент, когда система находится в промежуточном состоянии

**Как это сделало бы решение недостижимым:**

Предположим, что при создании возврата нужно одновременно:

1. Создать запись в БД возвратов (`status = CREATED`)
2. Заблокировать прямое отправление в БД отправлений (`locked_for_return = true`)

Обе операции должны выполниться атомарно: либо обе, либо ни одна. Но базы разные, общая транзакция невозможна

**Проблема:**

Если первая операция (создать возврат) выполнилась, а вторая (заблокировать отправление) отказала (сервис отправлений недоступен), система оказывается в состоянии: возврат создан, но отправление не заблокировано. Клиент может попытаться создать второй возврат того же отправления

**Обход:**

**Не требовать блокировки прямого отправления при создании возврата.** Вместо этого:

1. **Проверка права на возврат (идемпотентная):** При создании возврата сервис возвратов вызывает API отправлений: «можно ли вернуть это отправление?" (оно вручено? срок не истёк? уже есть возврат?). Если нет - отказ. Если да - создаётся возврат

2. **Если проверка отказала из-за недоступности API отправлений:** Возврат создаётся с флагом `validation_pending = true`. Воркер повторяет проверку позже (пункт б)

3. **Блокировка не нужна:** Если клиент попытается создать второй возврат, проверка вернёт «уже есть возврат для этого ШПИ" - и второй возврат не создастся. Идемпотентность на уровне бизнес-правил, а не блокировки базы

**Принцип (занятие 7):** Не «как избежать промежуточного состояния", а «как жить с тем, что оно существует". Сделать его обнаружимым (флаг `validation_pending`), конечным по времени (воркер доводит до конца) и не приводящим к потере денег (проверка повторяется до успеха)

### Ограничение 4: Смежная корпоративная система недоступна для изменений

**Суть ограничения (занятие 5):**

Корпоративная шина данных, тарификатор, системы финансового учёта - это смежные системы, которыми не владеет команда кабинета. Нельзя добавить поле в событие шины или изменить логику тарификатора под фичу возвратов

**Как это сделало бы решение недостижимым:**

Предположим, что для расчёта стоимости возврата нужно знать «был ли товар вскрыт покупателем". Команда хочет, чтобы тарификатор учитывал этот признак при расчёте. Но тарификатор - внешняя система, команда не может добавить туда новое поле

**Проблема:**

Если фича возвратов **критически зависит** от изменения в смежной системе, её запуск блокируется до тех пор, пока владелец смежной системы не внедрит изменение. Это может занять месяцы

**Обход:**

**Спроектировать фичу так, чтобы она работала с текущим контрактом смежной системы.**

**Вариант 1:** Признак «товар вскрыт" фиксируется в сервисе возвратов при приёме на ПВЗ. Стоимость рассчитывается тарификатором по базовой модели (вес, расстояние), а сервис возвратов применяет коэффициент сверху (например, +50% если товар вскрыт). Логика возврата не ждёт изменений в тарификаторе

**Вариант 2:** Стоимость возврата фиксируется при создании заявки (тарификатор рассчитывает по текущей модели), а корректировка (если товар вскрыт) выполняется вручную при приёме на ПВЗ. Это не автоматизировано полностью, но фича запускается

**Принцип:** Критическая зависимость от изменения смежной системы - это риск проекта. Проектируйте фичу так, чтобы она работала с тем, что смежная система даёт сейчас. Если требуется изменение в смежной системе - вынесите его в отдельную задачу с собственным планом, а фичу запустите в усечённом виде

**Для фичи возвратов:** Тарификатор рассчитывает стоимость возврата как «обратное отправление того же веса". Если через полгода потребуется более сложная модель (например, учёт причины возврата) - это будет отдельная задача в бэклоге тарификатора, а сервис возвратов уже работает

### Ограничение 5: Событийная интеграция через брокер сообщений (RabbitMQ) без гарантии порядка

**Суть ограничения (занятие 6):**

RabbitMQ доставляет сообщения, но не гарантирует порядок обработки, если потребителей несколько или сообщения маршрутизируются по разным очередям. Событие «возврат создан" может прийти раньше события «возврат принят", если обработка второго задержалась

**Как это сделало бы решение недостижимым:**

Предположим, что витрина возвратов (пункт в) обновляется событийно: каждое событие `ReturnStatusChanged` сразу меняет запись в ClickHouse. Если события приходят не по порядку, запись может оказаться в некорректном состоянии

**Пример:**

1. Возврат создан (`status = CREATED`), событие `ReturnCreated` опубликовано
2. ПВЗ принял возврат (`status = ACCEPTED`), событие `ReturnStatusChanged(ACCEPTED)` опубликовано
3. Потребитель витрины обработал `ReturnStatusChanged(ACCEPTED)` раньше, чем `ReturnCreated`
4. В витрине запись с `status = ACCEPTED`, но без поля `created_at` - данные повреждены

**Обход:**

**Не обновлять витрину событийно, а использовать пакетный конвейер (пункт в):** Планировщик читает БД возвратов раз в сутки и грузит финальное состояние. Порядок событий не важен - читается текущее состояние из базы, где оно уже согласовано

**Для оперативной аналитики (если нужна):** Потребитель событий проверяет версию события (поле `event_version` или `occurred_at`) и отбрасывает устаревшие. Если пришло событие `status = CREATED` после `status = ACCEPTED` - игнорируется

**Принцип:** Не проектируйте критическую логику в расчёте на порядок событий, если брокер его не гарантирует. Либо читайте финальное состояние из базы (источник истины), либо добавьте версионирование событий

## Выводы

Архитектурные ограничения унаследованного ландшафта не делают решение невозможным, но требуют явного обхода:

1. **Публичный API как контракт** -> Выделить новый ресурс `/returns`, не перегружать `/shipments`
2. **Каждый сервис со своей базой** -> Создать сервис возвратов с БД возвратов
3. **Нет распределённой транзакции** -> Отложенная валидация + воркер, идемпотентность на уровне бизнес-правил
4. **Смежная система недоступна для изменений** -> Работать с текущим контрактом, сложная логика - на стороне сервиса возвратов
5. **Нет гарантии порядка событий** -> Пакетный конвейер витрины вместо событийного, источник истины - БД, а не очередь

Общий принцип: Ограничения ландшафта - это контекст проектирования, а не блокер. Решение проектируется с учётом ограничений, а не в надежде их обойти
