# Пункт (0) - Оценка и декомпозиция

**Фича:** Управление возвратами  
**Нотация:** C4 Container Diagram  
**Основа:** черновик практикума З-5

---

## Оценка фичи на верхнем уровне

**Что входит:**

1. Оформление возврата клиентом - по одному отправлению и списком (массовая операция)
2. Отслеживание возвратов - перечень, текущее состояние, причина возврата
3. Денежные последствия возврата для клиента - отдельным контуром (возврат средств или списание за услугу)
4. Оба входа в систему - экран (микрофронтенд + BFF) и программный интерфейс (шлюз)

**Что не входит:**

- Тарифная модель услуги возврата (владелец - тарификатор)
- Работа отделения при приёме возврата
- Сторона физического лица

**Два контура:**

- **Ядро:** возврат отправления (логистика) - отправление едет обратно
- **Следствие:** возврат денег (финансы) - сумма возвращается или списывается

Проектировать их как один процесс нельзя (занятие 5), так как в них участвуют разные смежные системы и разные правила

## Декомпозиция на сервисы и модули

### Затрагиваемые существующие контейнеры

| Контейнер | Что меняется | Обоснование |
|---|---|---|
| **Микрофронтенды (React)** | Новый экран "Возвраты": перечень, состояние, причина, оформление (одиночное и файлом) | Экран нужен для входа через веб |
| **web-client (BFF)** | Новые методы под экран возвратов | Собирают данные из REST API |
| **API Gateway** | Маршруты и лимиты для `/returns` | Вход интегратора-маркетплейса |
| **REST API** | Публичные методы `/returns` (создание, список, статус) | Общий контракт для обоих входов |
| **Сервис разбора файлов** | Формат "список возвратов" (массовое оформление) | Массовая операция - З-8 |
| **Сервис авторизации** | Право "возвраты" в ролях клиента | Разграничение доступа |
| **RabbitMQ** | Очереди событий возвратов (`ReturnCreated`, `ReturnStatusChanged`, `ReturnDelivered`) | Событийная интеграция - З-6 |
| **Сервис отслеживания РПО** | Публикует операции по возвратным отправлениям | Откуда берётся статус возврата |
| **Фоновая публикация в шину** | Публикует события возвратов в корпоративную шину данных | Связь с внешним контуром |
| **Онлайн Баланс** | Подписка на `ReturnDelivered`: списание за возврат или зачисление (при отказе в приёме) | Денежный контур - З-7 |
| **API отправлений** | Читает прямое отправление по ШПИ (проверка права на возврат, срок) | Проверка связи возврата с исходным отправлением |

### Новые контейнеры

#### Сервис возвратов (`return-service`)

**Назначение:**

- Жизненный цикл возврата (модель состояний - З-6)
- Связь возврата с прямым отправлением по ШПИ
- Причина возврата
- Валидация бизнес-правил (срок возврата не истёк, отправление вручено)

**Почему нельзя в существующих:**

1. **Не в REST API:** у возврата свой жизненный цикл, который меняется по своим причинам. Положить его в общий публичный контракт - значит смешать логику разных доменов в одном месте

2. **Не в API отправлений:** возврат - не подвид отправления, а самостоятельная сущность со связью на исходное. Возвратное отправление в почтовой сети - это новое физическое отправление, у него свой ШПИ

3. **Не в Онлайн Баланс:** там денежный контур. Склеивание возврата отправления и возврата денег запрещено постановкой (З-5)

4. **Критерий границы сервиса** (занятие 5): профиль нагрузки. Возвраты создаются на порядок реже, чем отправления. Выделение в отдельный сервис изолирует основной поток от возвратов и снижает риск влияния пиковой нагрузки возвратов на создание отправлений

#### БД возвратов (Postgres)

Хранит состояние возврата, связь с прямым отправлением, причину, историю переходов состояния. Новая база, так как у нового сервиса своя база (занятие 5)

## Обоснование решений

1. **Один новый сервис, а не сервис на каждую функцию:** Массовое оформление идёт через существующий сервис разбора файлов. Деньги - через Онлайн Баланс. Не создаём "Сервис массового оформления возвратов" и "Сервис финансовых операций возвратов"

2. **Два входа на схеме:** Веб (пользователь -> микрофронтенд -> BFF) и API (интегратор -> шлюз). Сходятся на REST API. Типовая ошибка З-5 - нарисовать один вход

3. **Денежный контур выделен:** Возврат отправления и возврат денег - разные смежные системы (тарификатор, API отправлений vs системы финансового учёта), разные правила (З-5, З-7)

4. **Протокол [?] там, где неизвестен:** Связь BFF -> files, ret -> notif, bal -> fin - источники не называют протокол, поэтому [?]. Это честность, а не дефект (занятие 5)
