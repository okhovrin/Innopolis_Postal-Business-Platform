# Пункт (г). Ролевая модель и матрица прав

Фича «Управление возвратами»

Клиент - юридическое лицо с договором

Пользователь - сотрудник, действующий от его имени

У одного клиента несколько сотрудников с разными полномочиями, поэтому роль описывает **характер работы**, а не должность

---

## 1. Четыре вопроса и четыре разных источника истины

| Вопрос | Как называется | Чем отвечается | Скорость изменения |
|---|---|---|---|
| Кто это? | Аутентификация | Токен, подписанный сервисом идентификации | Годы |
| От чьего имени? | Связь пользователя с клиентом | Признак `client_id` в токене и в сессии | Секунды (переключение) |
| Что ему можно? | Авторизация | Роль + принадлежность объекта | В любой момент |
| Что он сделал? | Аудит | Журнал операций | - |

Объединить их нельзя: у ответов разные источники истины и разная скорость изменения. Аутентификация кешируется (токен живёт 15 минут), авторизация - нет: проверка принадлежности объекта выполняется на каждом запросе

## 2. Роли

| Роль | Назначение | Уровень |
|---|---|---|
| **Интегратор** | Программа клиента: создаёт возвраты и читает их через API | Субаккаунт (техническая учётная запись) |
| **Оператор** | Сотрудник фронт-офиса: оформляет и отменяет возвраты, видит причины и статусы | Субаккаунт |
| **Финансист** | Отвечает за денежный контур: подтверждает приёмку, сверяет удержания и списания | Администратор аккаунта |
| **Ревизор** | Аудит: видит всё, ничего не меняет | Администратор аккаунта |

**Изменения против заготовки «администратор, оператор, бухгалтер»:**

- **«Интегратор» добавлен** - это машинный субъект, отдельный от людей
  В журнале аудита он должен быть отличим от сотрудника: иначе невозможно понять, ошибся человек или программа клиента
- **«Бухгалтер» переименован в «финансиста»** - роль отвечает не за учёт, а за операции с балансом: приёмку, списание, снятие удержания
- **«Администратор» разделён** - администратор аккаунта управляет правами и деньгами, но не оформляет возвраты; иначе он совмещает контроль и исполнение

## 3. Операции фичи

| № | Операция | Вход | Двигает деньги клиента |
|---|---|---|---|
| О1 | Создать возврат (API) | Интерфейс | Да - удержание |
| О2 | Создать возврат (экран) | Экран | Да - удержание |
| О3 | Получить перечень возвратов | Оба | Нет |
| О4 | Получить карточку возврата | Оба | Нет |
| О5 | Отменить возврат | Оба | Да - снятие удержания |
| О6 | Подтвердить приёмку на пункте | Экран | Да - списание |
| О7 | Выгрузить данные по возвратам | Экран | Нет |
| О8 | Просмотреть журнал изменений | Экран | Нет |

О1 и О2 - одна бизнес-операция с двумя входами. В матрице они разделены, потому что права на них различаются: интегратор не имеет доступа к экрану, оператор - к программному интерфейсу

## 4. Матрица в трёх измерениях

Измерения: **субъект** (роль) × **операция** × **область видимости** (множество объектов, над которыми операция разрешена). Пустая клетка - запрещено. Слово «все» без уточнения не используется

| Операция | Интегратор | Оператор | Финансист | Ревизор |
|---|---|---|---|---|
| **О1** Создать (API) | Возвраты своего клиента | - | - | - |
| **О2** Создать (экран) | - | Возвраты своего клиента | - | - |
| **О3** Перечень | Возвраты своего клиента | Возвраты своего клиента | Возвраты своего клиента | Возвраты своего клиента |
| **О4** Карточка | Возвраты своего клиента | Возвраты своего клиента | Возвраты своего клиента | Возвраты своего клиента |
| **О5** Отменить | Возвраты своего клиента в состоянии CREATED | Оформленные им, в состоянии CREATED | Возвраты своего клиента в состоянии CREATED | - |
| **О6** Приёмка | - | - | Возвраты своего клиента в состоянии CREATED | - |
| **О7** Выгрузка | - | - | Возвраты своего клиента | Возвраты своего клиента |
| **О8** Журнал | - | Возвраты своего клиента | Возвраты своего клиента | Возвраты своего клиента |

**Почему область везде «своего клиента».** Разные клиенты - разные юридические лица с отдельными договорами и балансами. Показать сотруднику одного клиента возврат другого - не ошибка прав, а утечка между клиентами

**Ограничение О5 для оператора.** Оператор отменяет только оформленные им самим возвраты. Это ограничение **не выражается ролью**: у двух операторов роль одинаковая. Оно выражается признаком объекта - `created_by == current_user`. Проверяется в обработчике отмены до выполнения операции

## 5. Как проверяется принадлежность в запросе

Формула «читаем X среди Y» для операции О4 (карточка возврата):

> Читаем **возврат по идентификатору** среди **возвратов, у которых `client_id` совпадает с `client_id` из токена**

Конкретно: запрос к БД имеет вид

```sql
SELECT * FROM returns
WHERE return_id = :return_id
  AND client_id = :client_id_from_token
```

Ключевое: `client_id` берётся из **проверенного токена**, а не из тела запроса, не из строки запроса и не из заголовка. Если бы клиент мог передать `client_id` сам, проверка принадлежности сводилась бы к проверке роли

Отсутствие строки даёт `404`, а не `403`: клиент не должен узнать, что объект с таким идентификатором существует у кого-то другого

**Для О5 (отмена) к условию добавляется признак авторства:**

```sql
SELECT * FROM returns
WHERE return_id = :return_id
  AND client_id = :client_id_from_token
  AND (created_by = :current_user OR :role IN ('финансист','интегратор'))
```

Так одно и то же условие обслуживает три роли с разными правилами: оператор ограничен авторством, финансист и интегратор - нет

## 6. Правило по умолчанию

**Операция, которой нет в матрице, запрещена всем.**

Это относится и к операциям, которые появятся завтра: новая операция попадает в систему закрытой и открывается явной записью в матрице. Обратное правило («разрешено, если не запрещено») недопустимо: любая забытая запись становится дырой

Практическое следствие: добавление операции требует двух изменений - реализации и строки в матрице. Расхождение между ними должно ловиться тестом, а не ревью

## 7. Модель контроля доступа и её обоснование

**Выбрана атрибутная модель (ABAC) с ролевым основанием**

Роль определяет *класс* доступных операций, но не даёт ответа на вопрос «над какими объектами». Ответ даёт атрибут - `client_id` объекта, `created_by`, `status`. Поэтому проверка всегда двухступенчатая: роль разрешает операцию, атрибуты сужают множество объектов

**Рассмотренные альтернативы**

*Чистая ролевая модель (RBAC).* Недостаточна: роли «оператор» мало - два оператора с одинаковой ролью должны видеть разные возвраты (только свои). Пришлось бы заводить роли вида «оператор-свой» и «оператор-все», и число ролей росло бы с каждой комбинацией

*Списки доступа на объекте (ACL).* Отвергнуты: возвратов много, они создаются постоянно, и запись списка на каждый объект при создании - лишняя работа и лишний источник расхождений. Кроме того, ACL плохо отвечает на вопрос «покажи все возвраты моего клиента»: пришлось бы собирать их перебором

*Сочетание: RBAC для операций + ABAC для объектов.* Это и выбрано - роль отвечает за «что можно», атрибуты за «над чем». Стоимость - проверка при каждом запросе; выигрыш - матрица остаётся маленькой, а правила принадлежности живут в одном месте (в запросе к БД), а не размазаны по ролям

**Почему не проверка только по роли.** Типовая ошибка: «проверяем права» - роль проверили, а чей это возврат, нет. Система с такой проверкой позволяет оператору клиента A отменить возврат клиента B, подставив чужой идентификатор. Проверка принадлежности - не украшение матрицы, а её обязательная третья координата
