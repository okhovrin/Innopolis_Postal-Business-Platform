# Интеграция с API возвратов

## Доступ

Используются Bearer и Client Credentials: пароль сотрудника в интеграции не хранится.

Администратор клиента подключает интеграцию, привязывает её к своему client_id и отдельному субъекту с ролью из матрицы, включает api_enabled и задаёт лимит. При подключении выдаются адрес внешнего API, адрес получения токена, client_id приложения и client_secret. Идентификатор приложения и идентификатор клиента-организации - разные значения.

API и получение токена доступны из внешней сети по HTTPS. Внутренний сервис идентификации через закрытую сеть не используется.

Получение токена, параметры TOKEN_URL, APP_ID и APP_SECRET берутся из настроек подключения:

```bash
curl --request POST "$TOKEN_URL" \
  --user "$APP_ID:$APP_SECRET" \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'grant_type=client_credentials' \
  --data-urlencode 'scope=returns:read returns:write returns:cancel'
```

Ответ поставщика содержит access_token, token_type=Bearer, expires_in и выданный scope. В TOKEN сохраняется access_token, в BASE_URL - адрес API без завершающего слеша. Пример адреса API - https://api.example.test, адрес токена - https://auth.example.test/oauth/token. При истечении токена программа снова получает его тем же способом. Недействительные реквизиты приложения исправляются при подключении, а не повтором бизнес-запроса.

В запросах к возвратам передаётся `Authorization: Bearer $TOKEN`. Отдельной подписи тела запроса в этом контракте нет: токен подписан поставщиком, программа предъявляет его по HTTPS. client_secret используется только для получения токена. Секреты и токены не кладутся в репозиторий и не записываются в журнал запросов.

Сервер проверяет подпись, издателя, назначение API, срок токена, отзыв, активную связь субъекта с клиентом, scope и текущую роль. Успешный вход не означает право читать любой return_id. Если источник текущих прав недоступен, операция получает 503 AUTHORIZATION_UNAVAILABLE.

## Операции

| Метод и путь | Назначение | Scope |
|---|---|---|
| POST /v1/return-jobs | Оформить возврат или список | returns:write |
| GET /v1/return-jobs/{job_id} | Читать состояние, результат и локальные статусы возвратов | returns:read |
| POST /v1/returns/{return_id}/cancel | Отменить до передачи | returns:cancel |

У API версия в пути /v1. Изменение смысла или обязательных полей потребует /v2.

## Оформить возврат

Клиент-организация определяется по токену и серверной связи, client_id в теле не передаётся. Одна строка содержит shipment_id и reason_code как непустые строки, weight_grams - положительное целое, если известно. В этом контракте CUSTOMER_REQUEST означает просьбу клиента, WRONG_ADDRESS - ошибочный адрес. Другие коды дают INVALID_ROW до согласования справочника.

```bash
curl --request POST "$BASE_URL/v1/return-jobs" \
  --header "Authorization: Bearer $TOKEN" \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: 3df2a126-7b8e-4c7e-85a3-76d9c2ad3150' \
  --data '{"items":[{"shipment_id":"s101","reason_code":"CUSTOMER_REQUEST"}]}'
```

```http
HTTP/1.1 202 Accepted
Location: /v1/return-jobs/j101
Retry-After: 5
Content-Type: application/json

{"job_id":"j101","status":"RECEIVED","status_url":"/v1/return-jobs/j101"}
```

202 означает только надёжный приём. Воркер проверяет строки отдельно. На входе проверяются JSON, наличие непустого items, права, ключ и общий размер. Неверная строка не отменяет остальные.

Для каждого нового задания создаётся новый UUID в Idempotency-Key. После таймаута, потери соединения или 503 повторяются тот же ключ и то же тело. Соответствие ключа и результата хранится 7 суток - допущение из ЛР-2. Тот же ключ с другим телом даёт 409 IDEMPOTENCY_CONFLICT. Порядок полей JSON не важен, порядок строк важен.

## Узнать результат

Вызывайте GET по status_url с тем же Bearer. Интервал опроса - 5 секунд, допущение ЛР-2. GET не меняет состояние, Idempotency-Key не нужен. Клиент может закрыть вкладку, обработка продолжится.

```bash
curl "$BASE_URL/v1/return-jobs/j101" \
  --header "Authorization: Bearer $TOKEN"
```

```json
{
  "job_id": "j101",
  "status": "COMPLETED",
  "results": [
    {
      "row_no": 1,
      "shipment_id": "s101",
      "return_id": "r501",
      "state": "REGISTERED",
      "state_updated_at": "2026-11-26T12:00:00Z",
      "outcome": "PROCESSED"
    }
  ]
}
```

RECEIVED - принято, PROCESSING - строки ещё обрабатываются, COMPLETED - каждая строка имеет итог, FAILED - обработка всего задания остановлена с error. При FAILED уже успешные строки не отменяются: сначала разберите results, не отправляйте весь список заново.

PROCESSED - регистрация подтверждена, REJECTED - окончательный отказ, INTERVENTION - нужны исправление или разбор. Пока строка исполняется, outcome отсутствует. state показывает текущее состояние заявки. postal_status и postal_updated_at добавляются, когда получен почтовый статус. Отсутствующий статус означает, что подтверждённых данных ещё нет. Время - UTC.

При сбое смежной системы GET остаётся HTTP 200, потому что чтение успешно. У незавершённой строки могут появиться pending_error и next_attempt_at:

```json
{
  "row_no": 1,
  "return_id": "r501",
  "state": "SENDING",
  "state_updated_at": "2026-11-26T12:00:00Z",
  "pending_error": {
    "code": "CIRCUIT_OPEN",
    "message": "Передача временно отложена",
    "details": [],
    "retry_after_seconds": 10
  },
  "next_attempt_at": "2026-11-26T12:00:10Z"
}
```

Повтор передачи делает воркер с прежним ключом. Клиент опрашивает задание, не создаёт новое удержание. Воркер выбирает время не раньше окончания паузы размыкателя и next_attempt_at из своей стратегии повторов; deadline_at не продлевается.

## Отменить

return_id берётся из результата задания. Отмена допустима в NEW и READY. В READY сначала освобождается удержание, поэтому 202 и CANCELLING ещё не означают возврат денег. Отмена и начало передачи конкурируют атомарно: если воркер уже начал SENDING, отмена получает 409.

```bash
curl --request POST "$BASE_URL/v1/returns/r501/cancel" \
  --header "Authorization: Bearer $TOKEN" \
  --header 'Idempotency-Key: 80ab0131-4e91-4c13-b295-26f14bf40421'
```

```http
HTTP/1.1 202 Accepted
Location: /v1/return-jobs/j101
Retry-After: 5
Content-Type: application/json

{"return_id":"r501","state":"CANCELLING","status_url":"/v1/return-jobs/j101"}
```

В NEW сразу возвращается 200 и CANCELLED. В CANCELLING повтор возвращает 202, после завершения - 200 и CANCELLED; новая задача RELEASE не создаётся. Запрос без тела, один ключ сохраняется для повторов. Проверка результата - GET исходного задания. Если освобождение осталось неподтверждённым до deadline_at, заявка станет MANUAL; повтор отмены вернёт 409 MANUAL_REVIEW_REQUIRED, нужен оператор.

При завершённой отмене до регистрации итог строки - REJECTED с кодом CANCELLED_BY_CLIENT, а состояние заявки - CANCELLED.

## Ошибки и действия клиента

Ошибка содержит code для программы, message для человека, details для полей.

```json
{
  "code": "INVALID_REQUEST",
  "message": "Поле items обязательно",
  "details": [{"field": "items", "code": "REQUIRED"}]
}
```

| HTTP / место | Код | Что делать |
|---|---|---|
| 400 | INVALID_REQUEST | Исправить конверт, параметры, наличие ключа; при отмене убрать тело |
| 401 | UNAUTHENTICATED | Получить действующий токен; повторить команду с прежним ключом |
| 403 | ACCESS_DENIED | Проверить роль, scope, связь с клиентом и api_enabled; без изменения доступа не повторять |
| 404 | NOT_FOUND | Проверить идентификатор и свою область видимости; это также ответ для чужого объекта |
| 409 | IDEMPOTENCY_CONFLICT | Сверить исходный запрос, не менять тело у прежнего ключа |
| 409 | INVALID_STATE | Прочитать задание; после начала передачи отмена этим методом запрещена |
| 409 | MANUAL_REVIEW_REQUIRED | Дождаться сверки оператором, не создавать новую заявку для обхода |
| 413 | JOB_TOO_LARGE | Разделить список на новые задания в пределах лимита |
| 429 | RATE_LIMITED | Ждать Retry-After, повторить с прежним ключом |
| 503 | SERVICE_UNAVAILABLE | Ждать Retry-After, повторить тот же запрос; успех мог быть сохранён до потери ответа |
| 503 | AUTHORIZATION_UNAVAILABLE | Дождаться восстановления проверки прав; прежний ключ сохраняется |
| error строки | INVALID_ROW | Исправить поля строки, отправить только её новым заданием |
| error строки | SHIPMENT_NOT_FOUND | Проверить идентификатор и принадлежность клиенту, чужие данные не раскрываются |
| error строки | ALREADY_DELIVERED, RETURN_EXPIRED, RETURN_NOT_ALLOWED | Возврат недопустим, автоматически не повторять |
| error строки | INSUFFICIENT_FUNDS, LIMIT_EXCEEDED | Пополнить баланс или согласовать лимит; затем новое задание только для этой строки |
| error строки | ACCESS_DENIED | Право отозвано после приёма задания; восстановить доступ перед новым оформлением |
| error строки | PRICE_UNAVAILABLE | По ЛР-2 заявка REJECTED с технической причиной; после восстановления можно создать новую |
| error строки | CANCELLED_BY_CLIENT | Отмена завершена, повторное оформление только как новое намерение |
| pending_error строки | CIRCUIT_OPEN | Внешний вызов не сделан, воркер ждёт паузу; читать задание |
| pending_error строки | DEPENDENCY_UNAVAILABLE, DEPENDENCY_TIMEOUT | Вызов был сделан, результат неизвестен или сервис отказал; воркер сверяет и повторяет по ключу |
| error строки | MANUAL_REVIEW_REQUIRED | Автоповторы завершены, требуется сверка, неизвестное не считать отказом |

## Ограничения

Допущения из ЛР-2: задание не более 1000 строк и 5 МиБ, опрос каждые 5 секунд, ключ задания хранится 7 суток, технические повторы идут до 24 часов с создания задачи. Новый контракт отмены использует тот же срок хранения ключа. Лимит поддерживает небольшой поток ММСБ; большой список клиент делит сам.

Допущение ЛР-3: квота внешнего входа - 1000 запросов за календарные сутки UTC на клиента, включая GET и повторы. При исчерпании - 429 с Retry-After до сброса. Опрос нужно остановить после получения нужного результата.
