## Три операции

| Операция | Метод и путь | Связь с ЛР-2 |
|---|---|---|
| createReturnJob | POST /v1/return-jobs | Принимает список, затем создаются заявки NEW и выполняется конвейер |
| getReturnJob | GET /v1/return-jobs/{job_id} | Читает задание, построчный результат и текущий локальный снимок состояний |
| cancelReturn | POST /v1/returns/{return_id}/cancel | NEW -> CANCELLED или READY -> CANCELLING; затем RELEASE -> CANCELLED |

Для одного возврата используется список из одной строки,отмена после SENDING запрещена.

## Интеграционная карта

Круг 1 - команда кабинета, круг 2 - другая команда организации, круг 3 - внешний поставщик. Круги взяты из занятия 13; [?] означает неизвестную часть контракта.

| Связь по функции | Операция | Круг | Задача и кто начинает | Протокол | Доставка и требование | При отказе |
|---|---|---|---|---|---|---|
| Сервис идентификации и текущих прав | Все, вход через API | 2 | Программа -> поставщик за токеном; API -> источник текущих прав | OAuth 2.0, HTTPS; проверка прав [?] | Чтение можно повторить, права не выдаются без подтверждения | Стоп: 401 для плохого токена, 503 AUTHORIZATION_UNAVAILABLE при невозможности проверить права |
| Данные исходного отправления | createReturnJob | 2 для источника отправлений | Воркер REST API -> источник; получить принадлежность и допустимость | [?] | Чтение с повтором; чужой и отсутствующий объект не раскрывается | Отложить при техническом сбое; SHIPMENT_NOT_FOUND при подтверждённом отсутствии в своём клиенте |
| Тарификатор | createReturnJob, после 202 | 2 | REST API -> тарификатор; получить цену | [?] | Один вызов на попытку оформления, цена нужна до HOLD | Стоп строки: PRICE_UNAVAILABLE, NEW -> REJECTED, как в ЛР-2 |
| Онлайн Баланс | createReturnJob: HOLD; cancelReturn: RELEASE | 1, за ним финансовые системы - 2 | REST API -> Онлайн Баланс; отдать команду и получить подтверждение | HTTP/JSON; связь с учётными системами [?] | Повторы по client_id + return_id + типу операции, атомарная дедупликация | Отложить: WAIT_HOLD или CANCELLING; по сроку MANUAL |
| API отправлений | createReturnJob, после удержания | 2 | Воркер REST API -> API отправлений; передать запрос на регистрацию | [?] | Повторы с устойчивым ключом и сверкой результата; без поддержки ключа - ручной разбор | Отложить: SENDING, pending_error; здесь размыкатель |
| Отслеживание и корпоративная шина | getReturnJob: локальный почтовый статус; физический приём для DEBIT | 1 для отслеживания, 2 для шины | REST API -> отслеживание за снимком; отслеживание -> шина за операциями | HTTP/JSON; к шине REST через обвязку | Гарантия исходного потока [?]; операции дедуплицируются | Деградация: последний статус с временем обновления, без неподтверждённого DEBIT |
| RabbitMQ и сбор показателей | Уведомление после регистрации в createReturnJob | 1 | REST API -> RabbitMQ -> сбор показателей; отдать ReturnRegistered | AMQP - допущение ЛР-2 | Outbox и повторы, получатель пропускает повторный event_id | Отложить аналитику, REGISTERED не откатывается |

getReturnJob читает сохранённое задание и снимки. cancelReturn сначала сохраняет отмену, затем воркер обращается к Онлайн Балансу. Поэтому отказ смежной системы после надёжного приёма не заменяет HTTP-ответ команды на 503. Сбой BFF или API Gateway не останавливает уже принятые задания.

Размыкатель стоит на REST API -> API отправлений. При открытой цепи есть что делать: сохранить задачу и next_attempt_at, показать ожидание и не занимать ресурс внешним вызовом. Реальный адаптер должен перевести ответы в классы ошибок из breaker.py.

### События, граница и общий клиент

Наружу в этом контракте используется опрос, веб-хук не добавляется. Возможное уведомление клиенту о регистрации потребовало бы адреса получателя, подписи тела, повторов и обработки дублей, это отдельная функция.

Вне кабинета находятся физический приём и движение отправления в почтовой сети. Кабинет отвечает только за сохранение задания, состояния, денежное намерение и показ подтверждённых данных.

## Что изменилось относительно черновиков

| Основа | Изменение и причина |
|---|---|
| З-10 и ЛР-2 | Сохранены POST/GET return-jobs, добавлена отмена по существующим переходам NEW и READY |
| Условие З-11 | Временное окно, доля отказов, минимум вызовов и исключение ошибок запроса дополнены HALF_OPEN с одной пробой, растущей паузой и пределом времени |
| Материал З-12 | Матрица включает объектную область и программный вход; администратор ограничен своим клиентом, аудитор только читает |
| Материал З-13 | У каждой связи указаны инициатор, доставка и отказ |

Уточнение: размыкатель работает после ответа 202, поэтому CIRCUIT_OPEN передаётся в pending_error строки при GET 200, а не как ошибка уже принятого POST.
