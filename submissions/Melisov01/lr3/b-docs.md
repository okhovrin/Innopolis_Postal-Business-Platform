# (б) Возвраты через API: руководство интегратора

[К оглавлению](README.md) · [Спецификация OpenAPI](a-openapi.yaml)

Это руководство для разработчика системы клиента: склада, магазина, учётной системы. По нему можно оформить возврат и отследить его без экрана кабинета. Точная схема полей — в [a-openapi.yaml](a-openapi.yaml) (открывается в Swagger Editor). Ниже — всё, чего в схеме нет.

> Адреса в примерах — заглушки (`api-host.example`, `auth-host.example`). Настоящие адреса указаны в кабинете, в разделе «Настройки интеграции». Суммы и сроки в примерах — учебные допущения.

## 1. Что умеет API

| Операция | Запрос | Что делает |
|---|---|---|
| Оформить возврат | `POST /v1/returns` | Создаёт заявку на обратную пересылку исходного отправления. Ответ `202`: заявка принята, оформление идёт в фоне. |
| Запросить закрытие | `POST /v1/returns/{returnId}/close` | Просит закрыть возврат, пока отправление не принято в отделении. Если приёма не было, удержание будет освобождено. |
| Перечень возвратов | `GET /v1/returns` | Возвраты вашей организации с отбором: по номеру, ШПИ, состоянию, времени изменения. Так же узнают исход оформления и закрытия. |

Уведомлений (веб-хуков) нет: состояние узнают опросом (раздел 6).

## 2. Как получить доступ

**Шаг 1. Сервисная учётная запись.** Администратор аккаунта вашей организации заводит в кабинете (раздел «Настройки интеграции») учётную запись интеграции. Это учётная запись **программы**, а не сотрудника. Ей выдаются:

- `client_id` — открытый идентификатор;
- `client_secret` — секрет; показывается **один раз** при выпуске;
- области действия: `returns:read`, `returns:write`, при необходимости `returns:money:read` (суммы);
- привязка к организации и, если нужно, к субаккаунту. Тогда программа видит только возвраты этого субаккаунта.

Не используйте логин и пароль сотрудника: при смене пароля или увольнении сотрудника интеграция остановится, а все действия программы запишутся на человека.

**Шаг 2. Токен доступа (OAuth 2.0 Client Credentials).** Секретом `client_secret` подписывается запрос токена. Сам `client_secret` в запросы к API не передаётся.

```http
POST /oauth2/token HTTP/1.1
Host: auth-host.example
Content-Type: application/x-www-form-urlencoded
Authorization: Basic base64(client_id:client_secret)

grant_type=client_credentials&scope=returns:read%20returns:write
```

```json
{ "access_token": "eyJhbGciOi...", "token_type": "Bearer", "expires_in": 900, "scope": "returns:read returns:write" }
```

`expires_in` — время жизни в секундах (в примере 15 минут, допущение). Токена обновления нет. Когда токен истекает или API отвечает `401`, запросите новый тем же способом. Храните токен в памяти и используйте повторно, а не запрашивайте перед каждым вызовом.

**Шаг 3. Вызовы API** — с заголовком `Authorization: Bearer <access_token>`.

Хранение секрета: `client_secret` хранится только на сервере вашей системы, в хранилище секретов. Его нельзя класть в мобильное приложение, браузер или репозиторий. Если секрет утёк, администратор отзывает его в кабинете и выпускает новый. Старый перестаёт действовать сразу, а уже выданные по нему токены работают до истечения (до 15 минут).

## 3. Условия доступа, которых нет в описании методов

Если адрес и токен верны, а ответа нет, причина почти всегда в одном из этих пунктов.

| Условие | Что это значит для вас |
|---|---|
| **Сетевой контур** | API доступен из интернета **только через внешний шлюз**, по HTTPS (TLS 1.2+). Адрес шлюза — в «Настройках интеграции». Внутренние адреса организации снаружи недоступны. Токен выдаёт **внешнее** исполнение сервиса идентификации, его адрес тоже в настройках. Внутреннее исполнение работает только в закрытой сети организации, и запрос к нему просто не дойдёт. |
| **Тестовый и продуктивный контуры** | Адреса шлюза и выдачи токена у них разные, учётные записи интеграции тоже разные: тестовый `client_id` не работает в продуктивном контуре, и наоборот. Деньги в тестовом контуре не списываются. Метод может появиться в тестовом контуре раньше, чем в продуктивном. Если метод отвечает `404` без тела в формате ошибки, он ещё не открыт на шлюзе этого контура. |
| **Список разрешённых адресов** | Если администратор включил ограничение по IP, запросы с других адресов отклоняются на шлюзе (`403`). Добавьте исходящий адрес вашего сервера в настройках. |
| **Предел частоты и суточная квота** | Шлюз ограничивает частоту запросов одной учётной записи интеграции и общее число запросов в сутки. Текущий расход виден в «Настройках интеграции». При превышении приходит `429` с `Retry-After`. Значения пределов указаны в настройках: они зависят от договора, и в документации их нет. |
| **Размер запроса** | Тело запроса — не больше 64 КиБ (допущение). Перечень — не больше 100 записей на страницу. |
| **Время** | Все даты в UTC, формат ISO 8601 (`2026-11-26T09:15:02Z`). |
| **Таймаут на вашей стороне** | Ставьте не меньше **10 с**. Внутренний таймаут проверки отправления 3 с, поэтому за 10 с вы получите ответ, даже если смежная система не ответила. |
| **Права** | Оформлять и закрывать — область действия `returns:write`, читать — `returns:read`. Суммы в ответе видны только с `returns:money:read`, без неё `amount = null`. |

## 4. Оформить возврат: пример

**Ключ идемпотентности.** Перед первой отправкой сгенерируйте UUID на этот возврат и **сохраните его рядом с вашей записью о возврате**. При любом повторе (таймаут, обрыв, `5xx`, `429`) отправляйте **тот же** ключ и **то же** тело. Тогда второй заявки и второго удержания не будет.

```http
POST /v1/returns HTTP/1.1
Host: api-host.example
Authorization: Bearer eyJhbGciOi...
Idempotency-Key: 7d3c9f0e-2a41-4c8b-9a6e-1f2b3c4d5e6f
Content-Type: application/json

{
  "sourceBarcode": "80080012345678",
  "reasonCode": "RECIPIENT_REFUSED",
  "clientReference": "order-2026-11-000123"
}
```

Ответ — заявка принята:

```http
HTTP/1.1 202 Accepted
Location: /v1/returns?returnId=ret_01JD6T2Q8X4M
Retry-After: 5
Content-Type: application/json

{
  "returnId": "ret_01JD6T2Q8X4M",
  "sourceBarcode": "80080012345678",
  "returnBarcode": null,
  "reasonCode": "RECIPIENT_REFUSED",
  "clientReference": "order-2026-11-000123",
  "status": "queued",
  "reconciling": false,
  "createdAt": "2026-11-26T09:15:02Z",
  "updatedAt": "2026-11-26T09:15:02Z",
  "tracking": null,
  "settlement": { "status": "none", "amount": null, "currency": "RUB" }
}
```

`202` означает «принято», а не «оформлено». Сохраните `returnId`. Встречный ШПИ (`returnBarcode`) появится, когда возврат перейдёт в `awaiting_acceptance`.

Ключ хранится 24 часа. Если повторить запрос позже, тот же возврат не создастся дважды: ответ будет `409 RETURN_ALREADY_EXISTS` с номером существующей заявки в `details.existingReturnId`.

## 5. Закрыть возврат и прочитать перечень

```http
POST /v1/returns/ret_01JD6T2Q8X4M/close HTTP/1.1
Authorization: Bearer eyJhbGciOi...
Idempotency-Key: 0b8e2d4c-7f15-4a63-8e2a-5c9d1b7f3a20
Content-Type: application/json

{ "comment": "Клиент забрал отправление сам" }
```

Ответ `202` с `status: "closing"`. Исход определяет почтовая система: если отправление уже приняли, возврат станет `accepted_settlement_open`, и закрыть его нельзя. Если приём исключён, возврат пройдёт `releasing → closed_without_acceptance`, и удержание освободится. Повторный запрос на закрытие безопасен: он вернёт текущее состояние.

```http
GET /v1/returns?status=awaiting_acceptance,closing&updatedFrom=2026-11-26T09:00:00Z&limit=50 HTTP/1.1
Authorization: Bearer eyJhbGciOi...
```

Ответ — `{ "items": [ ... ], "nextCursor": "..." }`. Следующую страницу запрашивают с `cursor=<nextCursor>` и теми же отборами. Если `nextCursor = null`, страниц больше нет. Возвраты чужих организаций в перечень не попадают никогда. Если запросить чужой `returnId`, придёт пустой список.

## 6. Состояния и как часто опрашивать

| `status` | Что значит | Что делать |
|---|---|---|
| `queued`, `holding`, `registering` | Оформление идёт: проверка, удержание стоимости, регистрация встречного отправления | Опрашивать каждые **5 с** первые 2 минуты, затем раз в минуту |
| `awaiting_acceptance` | Есть встречный ШПИ, ждём приёма в отделении | Опрашивать **не чаще раза в час**: приём занимает дни, а не секунды. Можно закрыть. |
| `closing`, `releasing` | Проверяется закрытие или освобождается удержание | Раз в минуту |
| `accepted_settlement_open` | Отправление принято, расчёт не завершён | Раз в час. Это **точка невозврата**, закрыть нельзя. |
| `completed`, `rejected`, `closed_without_acceptance` | Конечные состояния | Больше не опрашивать. Причина отказа — в `rejection.code` (например, `RETURN_PERIOD_EXPIRED`, `INSUFFICIENT_FUNDS`). |
| незнакомое значение | Появилось в новой версии контракта | Считать «в обработке» и продолжать опрос |

- `reconciling: true` — исход внешней операции потерян и сверяется. Ждите, ничего не повторяйте.
- `tracking.stale: true` — свежих почтовых данных давно нет. Это **не** значит, что отправление не приняли.
- Опрашивайте одним запросом все свои незавершённые возвраты (`updatedFrom` = время прошлого опроса), а не каждый возврат по отдельности. Так вы экономите суточную квоту.

## 7. Что делать при каждой ошибке

Ошибка состоит из трёх частей: код протокола, `error.code` и `error.message`. Решения принимайте по **коду протокола и `error.code`**. `error.message` — для человека, его текст может меняться. `error.retryable` подсказывает, есть ли смысл повторять.

```json
{ "error": { "code": "CIRCUIT_OPEN", "category": "circuit_open", "message": "Проверка отправлений временно приостановлена; повторите через 7 с",
             "retryable": true, "retryAfterSeconds": 7, "dependency": "shipments", "requestId": "f00d..." } }
```

| Код | `error.code` | Что случилось | Что делать |
|---|---|---|---|
| 400 | `VALIDATION_FAILED` | Неверное поле (подробности в `details.fields`) | Исправить данные. Тот же запрос не повторять. |
| 401 | `TOKEN_MISSING`, `TOKEN_INVALID`, `TOKEN_EXPIRED` | Нет токена, он неверен или истёк | Получить новый токен и повторить **один раз**. Если снова `401` — проверить `client_id`/`client_secret` и контур. |
| 403 | `SCOPE_MISSING` | У учётной записи нет нужной области действия | Попросить администратора аккаунта добавить права. Не повторять. |
| 403 | `SUBACCOUNT_LIMIT_EXCEEDED` | Исчерпан лимит субаккаунта на сумму удержаний | Обратиться к администратору аккаунта. Не повторять. |
| 403 | без тела в формате ошибки | Запрос отклонён шлюзом по списку разрешённых адресов | Добавить ваш IP в настройках. |
| 404 | `SOURCE_SHIPMENT_NOT_FOUND` | У вашей организации нет такого исходного отправления | Проверить ШПИ и то, что отправление оформлено от **вашей** организации или субаккаунта. |
| 404 | `RETURN_NOT_FOUND` | Нет такого возврата среди ваших | Проверить `returnId`. |
| 409 | `RETURN_ALREADY_EXISTS` | По отправлению уже есть незакрытый возврат | Использовать `details.existingReturnId`. Новую заявку не создавать. |
| 409 | `INVALID_STATE` | Закрытие невозможно в текущем состоянии (`details.currentStatus`) | Из `queued`, `holding`, `registering` повторить, когда станет `awaiting_acceptance`. Из `accepted_settlement_open` и конечных состояний не повторять. |
| 409 | `IDEMPOTENCY_IN_PROGRESS` | Первый запрос с этим ключом ещё выполняется | Повторить **тот же** запрос через `Retry-After` с |
| 422 | `RETURN_NOT_ALLOWED` | Отправление нельзя вернуть: срок истёк или состояние не допускает (`details.reason`) | Не повторять |
| 422 | `IDEMPOTENCY_KEY_REUSED` | Ключ уже использован с другим телом | Ошибка в вашей программе: на новый возврат нужен новый ключ |
| 429 | `RATE_LIMITED` | Превышен предел частоты или квота | **Временная.** Ждать `Retry-After` с, повторить с тем же ключом. Снизить частоту опроса. |
| 500 | `INTERNAL_ERROR` | Сбой кабинета, исход неизвестен | **Временная.** Повторить с **тем же** ключом через 1, 2, 4, 8, 16 с (не больше 5 попыток). Если заявка успела создаться, вернётся она же. Дальше — в поддержку с `requestId`. |
| 503 | `DEPENDENCY_UNAVAILABLE` | Сервис отправлений не ответил, заявка **не** создана | **Временная.** Повторить с тем же ключом не раньше `Retry-After`, дальше с растущей паузой (5, 10, 20… с, до 5 минут). |
| 503 | `CIRCUIT_OPEN` | Проверка отправлений приостановлена после серии отказов. Ваш запрос **никуда не отправлялся**, заявка не создана. | **Временная.** Повторить с тем же ключом **ровно через `Retry-After` с**. Раньше бесполезно: придёт тот же мгновенный ответ. Это не ошибка в ваших данных, исправлять ничего не нужно. |
| таймаут или обрыв на вашей стороне | — | Исход неизвестен | Повторить с **тем же** ключом и телом. Это безопасно. |

Ошибки `4xx`, кроме `401`, `409 IDEMPOTENCY_IN_PROGRESS` и `429`, означают «вы неправильно попросили»: повтор без изменений даст тот же ответ. Ошибки `5xx` и `429` означают «мы не смогли, попробуйте позже». Незнакомый `error.code` обрабатывайте по коду протокола и `retryable`: перечень кодов может расширяться.

## 8. Совместимость

- Путь содержит мажорную версию `/v1`. Ломающие изменения выходят только в `/v2`, а `/v1` продолжает работать.
- В рамках `/v1` могут появиться новые поля ответа, новые значения `status` и `reasonCode`, новые `error.code`. **Игнорируйте незнакомые поля** и обрабатывайте незнакомые значения так, как сказано выше.
- Новое обязательное поле в запросе `/v1` не появится. Если оно понадобится, в `/v1` оно будет необязательным со значением по умолчанию.

## 9. Поддержка

В обращении укажите `requestId` из ответа или передайте свой `X-Request-Id`, время запроса (UTC) и `returnId`. Секреты и токены в обращение не вкладывайте.
