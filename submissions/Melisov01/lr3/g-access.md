# (г) Роли и матрица прав

[К оглавлению](README.md) · [Спецификация](a-openapi.yaml)

## От чего отталкиваюсь

- Клиент — это организация с договором. Пользователь — сотрудник, который работает от её имени. Один человек может работать за несколько организаций (занятие 12).
- У клиента есть материнский аккаунт и субаккаунты. У субаккаунта свои лимиты, а баланс общий, у материнского аккаунта (занятие 12).
- Пользователей у одного клиента могут быть сотни. Значит, раздавать права должен сам клиент, через своего администратора.
- Оформление возврата удерживает деньги (З-7). То есть право «оформлять» — это фактически право тратить деньги клиента.

Роли «оператор», «финансы», «аудитор» — проектное предложение. В фактах курса есть только администратор аккаунта и субаккаунт.

## Роли

| Кратко | Кто | Как входит |
|---|---|---|
| АА | Администратор аккаунта | через кабинет |
| ОП | Оператор возвратов: оформляет и ведёт возвраты. Может быть в материнском аккаунте или в субаккаунте | через кабинет |
| ФН | Финансы: смотрит удержания и списания | через кабинет |
| АУ | Аудитор: видит всё своего клиента, ничего не меняет | через кабинет |
| ИН | Учётная запись интеграции — это программа, а не человек. Привязана к клиенту и, если нужно, к субаккаунту | по `client_id` и `client_secret` (OAuth 2.0 Client Credentials) |

У человека может быть несколько ролей.

## Области видимости

C — клиент из токена, S — субаккаунт пользователя (если есть). Оба значения сервер берёт из токена, а не из запроса.

- **R(C)** — все возвраты клиента C;
- **σ(u)** — «своя область»: R(C), если пользователь в материнском аккаунте, или только возвраты его субаккаунта;
- **Sh(σ)** — исходные отправления из той же области;
- **σᴬ** — возвраты из своей области в статусе `awaiting_acceptance` (только их можно закрыть);
- **U(C)** — пользователи и учётные записи интеграции клиента;
- **A(C)** — журнал аудита клиента;
- **∅** — нельзя.

## Матрица

В каждой клетке — над какими объектами разрешена операция. Правило по умолчанию: всё, что не разрешено явно, запрещено. У новой роли или операции прав нет, пока их не добавили в матрицу.

| Операция | АА | ОП | ФН | АУ | ИН |
|---|---|---|---|---|---|
| Вход через API: получить токен | ∅ | ∅ | ∅ | ∅ | токен только для своего C (и S), с правами не шире выданных |
| Выпустить или отозвать учётную запись интеграции (только в кабинете) | U(C) | ∅ | ∅ | ∅ | ∅ |
| `createReturn` | отправления из Sh(C) | отправления из Sh(σ) + лимит субаккаунта | ∅ | ∅ | отправления из Sh(σ), нужно `returns:write`, + лимит |
| Пакетное оформление (из ЛР-2, в спецификации нет) | то же, до 100 строк | то же + лимит | ∅ | ∅ | то же |
| `closeReturn` | R(C)ᴬ | σᴬ | ∅ | ∅ | σᴬ, нужно `returns:write` |
| `listReturns` | R(C) | σ(u) | R(C) | R(C) | σ, нужно `returns:read` |
| Суммы в `listReturns` | R(C) | σ(u) | R(C) | R(C) | σ, только с `returns:money:read`, иначе `null` |
| Назначать роли | U(C), кроме себя | ∅ | ∅ | ∅ | ∅ |
| Смотреть журнал аудита | A(C) | ∅ | ∅ | A(C) | ∅ |

Что важно:

- Нигде нет «все возвраты» или «все пользователи». Любая область начинается с «своего клиента».
- Оператор из субаккаунта не видит возвраты соседнего субаккаунта, хотя клиент у них общий.
- Закрыть можно только возврат в `awaiting_acceptance`. Свой возврат в другом статусе даёт `409`, чужой — `404`.
- Администратор не может менять свои роли, а последнего администратора нельзя снять.

## Как проверяется принадлежность в каждой операции

Принадлежность не проверяется после чтения объекта, а сразу входит в запрос к базе (занятие 12): ищем «возврат X среди возвратов клиента C», а не «возврат X, потом проверяем, чей он».

| Операция | Где ограничивается | Что будет с чужим объектом |
|---|---|---|
| `createReturn` | проверка в API отправлений: «ШПИ среди отправлений клиента C (субаккаунта S)». Новая заявка получает `client_id` и `subaccount_id` из токена. Таких полей в теле нет, лишние поля отклоняются | `404 SOURCE_SHIPMENT_NOT_FOUND`, как будто отправления нет |
| `closeReturn` | `WHERE return_id = :id AND client_id = :C [AND subaccount_id = :S]` | `404 RETURN_NOT_FOUND` |
| `listReturns` | к любому отбору добавляется `client_id = :C [AND subaccount_id = :S]`, параметра `clientId` нет | пустой список |
| Вход через API | токен выпускается с `client_id`, `subaccount_id` и правами этой учётной записи | `401` |

Шлюз проверяет токен и его права, то есть что можно делать. Над какими объектами — проверяет сервис возвратов, потому что шлюз не знает, чей возврат.

## Что не выражается ролью

- Субаккаунт видит только свои возвраты — это зависит от поля объекта `subaccount_id`.
- Лимит субаккаунта на сумму удержаний — это число, разное у разных субаккаунтов. При превышении — `403 SUBACCOUNT_LIMIT_EXCEEDED`.
- Закрыть можно только в определённом статусе — зависит от состояния объекта.
- Программа видит суммы только с отдельным правом — клиент решает это для каждой интеграции.

## Выбор модели

Роли — для операций, атрибуты — для области видимости и лимитов. Списки доступа не используются.

- **Только роли** не подходят: субаккаунт, лимит и статус ролью не выразить. Пришлось бы делать роль «оператор субаккаунта 17» для каждого субаккаунта. Но для операций роли удобны: видов работы мало, и про любого человека сразу понятно, что он может.
- **Только атрибуты** тоже плохо: на вопрос «что может этот человек» тогда трудно ответить, а администратору клиента сложно управлять такими правилами.
- **Списки доступа** не подходят: возвратов очень много, а права у них одинаковые. Пришлось бы вести список на каждый возврат.

Проверка модели — добавление роли «аудитор». Это один новый столбец: просмотр по R(C), остальное ∅. Новые операции аудитору сами не достаются. При росте числа пользователей до сотен матрица не меняется: администратор только назначает больше ролей.

## Отзыв прав

- Роль сотрудника читается при каждом запросе, поэтому отзыв действует сразу.
- Права программы записаны в токене. Без доп. проверки отзыв подействует, только когда токен истечёт (до 15 минут, допущение). Поэтому для `createReturn` и `closeReturn`, где движутся деньги, сервис при каждом запросе ещё раз проверяет, что учётная запись не отозвана. Для `listReturns` такое окно допустимо.

## Аудит

Для `createReturn` и `closeReturn` в журнал записываются: кто (id пользователя или учётной записи интеграции, а не роль), от чьего имени (клиент и субаккаунт), что за операция и какой возврат, ШПИ, время, результат (успех или код ошибки), ключ идемпотентности, `requestId`, через что пришёл запрос (кабинет или API). Отказы тоже записываются: при разборе спора они важнее успехов. Электронная подпись здесь не требуется: спор разбирается по журналу и подтверждениям от финансовой системы.

## Найденное в чужой матрице

Матрицы одногруппников в репозитории нет, поэтому атаке подверглась учебная матрица из занятия 12 (ключ открыт уже после):

| Проблема | Как ею воспользоваться | Как закрыто в этой матрице |
|---|---|---|
| Карточка возврата — «все возвраты» | оператор клиента A перебирает номера и читает возвраты клиента B | нет областей шире R(C), чужой номер даёт 404 |
| Нет входа через API | интеграция работает по паролю сотрудника | отдельная роль ИН и отдельная строка «вход через API» |
| Нет правила по умолчанию | новая операция доступна всем | правило «запрещено всё, что не разрешено», ∅ записаны явно |
| Администратор может менять свои права | выдаёт себе что угодно | «кроме себя», последнего АА снять нельзя |
| Оформление списком без лимита | сотрудник субаккаунта тратит весь баланс | лимит субаккаунта на удержания |
| В аудите только роль | непонятно, кто и от чьего имени | записываются конкретный субъект, клиент и результат |
