## Вопросы к отчёту

| Вопрос владельца продукта | Какое решение поддерживает |
|---|---|
| Сколько зарегистрировано встречных отправлений по дням и причинам? | Определить, какой причиной возврата заняться в первую очередь и где не хватает данных о причинах. |
| По какому каналу заявки чаще отклоняются и сколько времени занимает успешная регистрация? | Улучшить форму, загрузку списка или инструкцию для API. Ошибки строк, отсеянных до создания заявки, смотрятся в отчёте о пакетном задании. |
| Какая сумма окончательно списана и скорректирована по завершённым расчётам, сколько принятых отправлений ещё ждут расчёта? | Выявить задержки и решить, какие операции передать на сверку. |

## Витрина

Одна строка факта `fact_return` соответствует **одной заявке** (`return_id`), в том числе отклонённой после создания. Она обновляется при получении новых подтверждений. Промежуточный журнал хранит одно событие на строку; денежные операции сводятся отдельно по ключу операции, прежде чем попадут в факт. Это защищает от умножения суммы при соединении с несколькими статусами трекинга.

| Поля факта | Откуда берутся |
|---|---|
| `requested_at`, `org_key`, `channel_key` | `ReturnRequested`: время, идентификатор организации в ЛК, канал при подаче. |
| `registered_at`, `accepted_at`, `state`, `rejection_code` | `ReturnStateChanged`: первая фиксация состояний «Ожидает приёма», «Принято, расчёт открыт», текущая версия заявки и причина отклонения. |
| `registration_seconds` | Разность `registered_at` и `requested_at` для зарегистрированных. До регистрации значение неизвестно. |
| `reason_key` | Нормализованная причина из `ReturnTrackingUpdated`; при отсутствии подтверждённого значения используется «неизвестно». Причина логистического возврата отделена от причины отказа в заявке. |
| `net_charged_minor`, `currency`, `settlement_open` | Подтверждения `ReturnMoneyConfirmed` по ключу операции и финальное состояние заявки. Сумма — списание плюс доначисление минус зачисленная разница. Удержание и его освобождение в выручку или окончательное списание не входят. |

В финансовом отчёте складываются только окончательно рассчитанные суммы, отдельно по каждой валюте. Подтверждённое отсутствие списания обозначается нулём; до завершения расчёта итоговая сумма неизвестна. Принятые отправления с незавершённым расчётом считаются отдельно. Так частичное списание не выдаётся за окончательное.

| Измерение | Зачем группировать | Откуда ключ |
|---|---|---|
| Дата заявки / дата регистрации | Сравнить спрос и фактическое оформление за разные дни. Для каждого вопроса используется своя дата. | Даты из времени создания заявки и перехода к ожиданию приёма. Дни определяются в московском времени. |
| Организация | Найти клиента, у которого регулярно зависает расчёт, и сверить его операции. | Идентификатор организации из ЛК. Связь с трекингом идёт через заявку и встречный ШПИ, с деньгами — через ключ операции. Внешние идентификаторы сами по себе не считаются идентификаторами клиента ЛК. |
| Канал подачи | Найти, где чаще возникают отказы и задержки. | Вход при создании: веб-форма, загрузка списка из веб-кабинета или API (индивидуальная и пакетная подача через API относятся к API). |
| Причина возврата | Выделить частые причины и проверить, что стоит менять в процессе отправки. | Исходный код почтовой операции и версионируемый справочник соответствия кодов. Если причина не установлена, используется отдельная категория. |

Основной агрегат `agg_return_day`: день регистрации `registered_day` × канал `channel_key` × причина `reason_key`, показатель `registered_count`. Он ускоряет регулярную сводку без повторного обхода журнала. Каждая зарегистрированная заявка попадает в одну группу; если причина уточнилась, агрегат для затронутого дня пересчитывается, и заявка переносится между группами. Для вопросов об отказах и расчётах витрина используется напрямую: доля отклонений показывается среди заявок с известным исходом оформления, ожидающие выводятся отдельно; среднее время считается только по зарегистрированным.

## Конвейер загрузки

Выбран **ELT**: статистика забирает события из RabbitMQ и сохраняет разрешённые поля в аналитическом журнале, затем строит факт, справочники и агрегат в хранилище. Маскировка и отбор полей выполняются до публикации. Адреса, тексты от клиентов и другие данные, не нужные для отчёта, в этот поток не отправляются.

При ETL можно было бы отправлять только готовый `reason_key`. Это сократило бы объём и упростило запросы, но неизвестный на момент загрузки `raw_reason_code` был бы потерян. Тогда после обновления справочника историческую причину восстановить нельзя. В ELT журнал позволяет пересчитать отчёт. Плата — хранение деталей и повторное построение затронутых данных. Отчёт не читает операционную БД возвратов при каждом просмотре.

Повтор события удаляется по `event_id`. Для состояния используется версия записи заявки; старое событие не заменяет более новое состояние. Для причины сохраняется версия почтовой операции: запоздалое сообщение не затирает уже подтверждённую более новую причину. Поздние данные пересчитывают затронутый день. Приём в журнал подтверждается потребителем после надёжной записи, чтобы потерянное подтверждение приводило к повтору, а не к пропуску.

**Прослеживаемость причины.** При обработке почтовой операции сервис возвратов сохраняет подтверждённый код и пишет `ReturnTrackingUpdated.raw_reason_code` в исходящее событие. Поле того же имени загружается в журнал с ключом и версией операции. При построении `fact_return.reason_key` сырой код сопоставляется с версией справочника; множество разных кодов может стать одной категорией. В `agg_return_day` остаётся категория и число заявок, поэтому для проверки значения можно вернуться к факту и исходному коду в журнале.

## Запрос к отчёту

Количество регистраций по дням и причинам в выбранном полуинтервале. `UNKNOWN` сохраняется отдельной строкой, а не исчезает из суммы.

```sql
SELECT
    registered_day,
    reason_key,
    SUM(registered_count) AS return_count
FROM agg_return_day
WHERE registered_day >= :from_day
  AND registered_day < :to_day
GROUP BY registered_day, reason_key
ORDER BY registered_day, reason_key;
```

## Граница актуальности

Отчёт показывает «Данные ЛК обработаны по состоянию на …», время последней успешной загрузки трекинга и признак задержки. При публикации витрины фиксируется последний непрерывный обработанный курсор событий; снимок фактов и агрегат публикуются вместе. Максимальное время отдельного события не подходит: оно может опередить недоставленные записи. Периодическая отметка источника отличает отсутствие новых операций от остановившейся доставки.

Граница относится к событиям, уже зафиксированным в ЛК. Она не обещает, что все физические операции, произошедшие к этому времени, уже пришли из почтовой сети. Задержка логистики и неразрешённый денежный исход показываются отдельно; при сбое сохраняется последняя согласованная версия отчёта.

Если причина неизвестна, возврат входит в общий счётчик и в группу `UNKNOWN`. Неизвестные суммы и длительности остаются `NULL`; они исключаются из суммы или среднего, а число таких записей выводится отдельно. При отсутствии известных сумм отчёт сообщает, что итог ещё не подтверждён.
