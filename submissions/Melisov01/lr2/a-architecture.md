## Как проходит запрос

Оба входа передают запрос в REST API: веб-клиент через BFF, программа клиента через API Gateway. Сервис возвратов получает проверенный контекст организации и повторно проверяет право оформить возврат и принадлежность отправления. В BFF и шлюзе правила возврата не дублируются. Оба входа позволяют создать заявку, прочитать её состояние и узнать исход пакетного задания.

Одиночный запрос сохраняет заявку и задачу на обработку в одной транзакции. В ответ приходит идентификатор и статус «ожидает проверки». Пакет сохраняется по тому же принципу, но идентификатор относится к заданию, а не к отдельному возврату. Предлагаемый ответ — HTTP `202 Accepted`, тело `{ "jobId": "…", "status": "queued" }` для пакета. Клиент повторяет потерянный запрос с прежним ключом и получает прежний идентификатор. Точный публичный контракт проектируется в ЛР-3.

Чтение состояния выполняется синхронно из сохранённых данных. Вызовы тарифов, логистики и баланса выполняются фоновым обработчиком с ограничением времени. Цепочка синхронных вызовов из браузера проще на успешном пути, но при сбое не сохраняет место остановки и заставляет клиента повторять запрос с неизвестным исходом.

## Массовое оформление

Граница проекта — **100 строк и 1 МиБ на входное задание** (учебное допущение: файл содержит идентификаторы и код причины, без вложений). Превышение отклоняется целиком до принятия с указанием лимита. Большой список делит отправитель; тогда он получает несколько идентификаторов и несколько результатов. Это упрощает ограничение очереди и изолирует большие загрузки. Внутреннее разбиение произвольного файла удобнее для клиента, но требует отдельной защиты при загрузке, квот по объёму и сборки отчёта по порциям.

1. Вход проверяет размер, доступ, читаемость структуры и число строк потоком, без обращений к смежным системам. Сервис сохраняет принятые строки и задачу в своей БД; строка хранится с номером в исходном файле. У API тот же предел по числу записей.
2. Воркер обрабатывает строки независимо, с ограниченной параллельностью на организацию. Формальная проверка строки проверяет наличие и формат ШПИ и причины. Бизнес-проверка выполняется для каждой заявки: отправление принадлежит организации, срок допустим, состояние исходного допускает операцию, встречное отправление ещё не оформлено. Затем применяются [переходы заявки](b-states.md).
3. Клиент опрашивает результат раз в **5 секунд** (учебное допущение: нужен видимый прогресс, а отдельный канал уведомлений не требуется). Прекращение опроса не останавливает задание. Результат можно получить позже; после завершения массового задания логистика и расчёты продолжают обновляться в карточке заявки.
4. Итог показывает количество строк в каждом из трёх множеств и выдаёт результат по строкам:

| Исход | Пример | Что делать |
|---|---|---|
| Обработано | Подтверждена регистрация встречного отправления. | Открыть заявку и отслеживать отправление по встречному ШПИ. Доставка ещё может не состояться. |
| Отклонено | Исходное отправление не принадлежит организации или срок возврата истёк. | Не повторять ту же строку; показывается причина без раскрытия чужих данных. |
| Требует вмешательства | Неверный формат ШПИ, недостаточно средств или исход внешней операции не удалось подтвердить. | Исправить данные или пополнить баланс и повторить только исправимые строки. При неизвестном исходе открыть связанную заявку; до сверки повторная регистрация блокируется. |

Принятое задание хранится вместе с отложенными задачами. Планировщик выбирает строки с наступившим `next_attempt_at`, проверяет срок аренды `lease_until` и в транзакции закрепляет задачу за воркером. После перезапуска незавершённую задачу можно подобрать снова. Один воркер продвигает проверку, удержание и регистрацию; точные переходы и ожидаемые ответы перечислены в [пункте (б)](b-states.md). Исход пакета фиксируется после результата всех строк. Поздняя сверка меняет связанную заявку; первоначальный отчёт пакета сохраняется как результат на момент завершения обработки.

**Повторы и сверка.** Учебные допущения для проекта: таймаут внешнего вызова **3 секунды**, паузы между повторными попытками **10, 30 и 90 секунд**, сверка незакрытых и недавних операций каждые **15 минут**. Параметры нужны, чтобы сбой одной зависимости не останавливал очередь; перед внедрением их проверяют на нагрузке. После исчерпания повторов вызывается сверка или передаётся задача оператору. Обещания, что недоступная система восстановится за это время, нет. Явный бизнес-отказ автоматически не повторяется. При потере ответа повторяется запрос статуса либо та же операция с тем же ключом, если смежная система гарантирует идемпотентность.

## Изоляция отказов

Для тарификатора, логистики и финансов задаются отдельные таймауты, лимиты параллельных вызовов и размыкатели цепи. При серии технических ошибок новые вызовы конкретной зависимости временно прекращаются; сохранённые задания остаются доступны для повтора. Лимиты фоновых задач отделены от чтения статусов. Бизнес-отказы в счётчик технических ошибок не входят.

| Где отказ | Что доступно и что видит клиент |
|---|---|
| Микрофронтенд или BFF | Не работает веб-вход. API и уже принятые задачи работают. Если веб-ответ потерян, повтор с тем же ключом возвращает прежний идентификатор. |
| API Gateway | Внешняя интеграция не может отправить или прочитать запрос через шлюз. Веб-вход и обработка принятых задач продолжаются. |
| Общий REST API | Недоступны оба входа. Воркер действует по сохранённым задачам, напрямую; клиент повторяет запрос после восстановления. |
| Сервис возвратов или его БД | Новая заявка не подтверждается, чтение и обработка приостанавливаются. Внешний эффект, выполненный перед сбоем, сверяется по прежнему ключу после восстановления. |
| API отправлений или логистическая система | Без проверки исходного новые возвраты не оформляются. При неизвестном результате регистрации или закрытия показывается «проверяем исход»; повтор с новым ключом и освобождение удержания блокируются. |
| Тарификатор | Новая стоимость не подтверждается, удержания по неподтверждённой цене нет. Уже оформленные возвраты доступны. При пересчёте после приёма расчёт остаётся незавершённым; логистика не блокируется. |
| Сервис отслеживания или корпоративная шина | Показан последний подтверждённый статус и время его получения. Отсутствие свежего события не считается подтверждением неприёма; окончательное списание по догадке не выполняется. |
| Онлайн Баланс | До подтверждения удержания встречное отправление не регистрируется. После приёма показывается «расчёт не завершён», почтовые статусы продолжают обновляться. Остаток, показанный в интерфейсе, не используется для разрешения расхода. |
| RabbitMQ, статистика или аналитическое хранилище | Оформление и трекинг продолжаются. Невыданные события остаются в журнале, доставка возобновляется после восстановления. Отчёт показывает последнюю согласованную версию и её границу актуальности; при отсутствии версии отчёт недоступен. |

## Деньги и повтор запроса

По учебному условию З-7 при оформлении удерживается предварительная стоимость, при приёме удержанная сумма списывается окончательно. Если приём исключён, удержание освобождается. Разница при изменении веса проводится отдельным доначислением или зачислением; при недостатке средств для доплаты расчёт остаётся открытым для вмешательства. Денежные подтверждения хранятся отдельно от трекинга.

Ключ входного запроса привязан к организации и типу операции. Повтор с тем же ключом и содержимым возвращает прежний результат; другое содержимое с прежним ключом отклоняется. Для каждой строки хранится связь с заявкой. На уровне бизнеса допускается одна незакрытая заявка на исходное отправление у организации; после подтверждённой регистрации новая заявка на тот же возврат блокируется. Так повтор через другой канал не создаёт второе удержание.

Вызовы регистрации и закрытия используют разные устойчивые ключи. Финансовый ключ — заявка, вид операции и номер операции: удержание, списание, освобождение или корректировка. Сумма и валюта фиксируются до вызова; повтор не генерирует новый ключ. Сверка сопоставляет журнал с авторитетным статусом регистрации и с выпиской финансового сервиса по внешним ключам, проверяет вид, сумму и результат. Если подтверждения расходятся с локальным состоянием, дальнейшие денежные команды блокируются до разрешения. Пока внешняя система не позволяет надёжно определить исход записи, автоматический повтор денежной команды не включается.
