# (г) Ограничения унаследованного ландшафта и способы их обхода

При проектировании фичи "Управление возвратами" нельзя опираться на идеальную архитектуру "с нуля". Ниже приведены четыре ограничения текущего технологического ландшафта системы и проектные решения, позволяющие реализовать фичу без переписывания платформы


## 1. Отсутствие распределённых транзакций и паттерна Saga между сервисами с собственными БД
* **Суть ограничения:** В системе около 60 микросервисов, каждый со своей изолированной базой данных PostgreSQL. Межсервисный координатор транзакций (Saga) в ландшафте не применяется. Попытка спроектировать оформление возврата как единую распределённую транзакцию "создать запись в `REST API` + удержать деньги в `Онлайн Балансе` + отправить в `Корпоративную шину`" сделала бы фичу недостижимой в рамках текущего стека
* **Как обойдено в проекте:**
  1. Использован паттерн Transactional Outbox в локальной БД `REST API`: заявка на возврат и задача на удержание средств/публикацию события записываются в одной локальной транзакции PostgreSQL
  2. Согласованность между контурами обеспечивается не мгновенным откатом, а планировщиками-воркерами с экспоненциальной паузой и периодической сверкой по идентифицирующим ключам (`return_id` + тип операции)


## 2. Неподконтрольность внешнего контура и двухуровневая модель состояний
* **Суть ограничения:** Личный кабинет обрабатывает только часть жизненного цикла отправления. Физический приём, сортировка и транспортировка возврата происходят во внешней учётной системе почтовой сети, контракты и скорость ответа которой команда кабинета не контролирует. Кроме того, клиентский справочник статусов схлопывает 10 причин возврата в один статус, что лишает клиента информации для принятия решений
* **Как обойдено в проекте:**
  1. **Разделение владельцев состояний:** Кабинет не пытается управлять физическими статусами возврата, а выступает витриной, принимающей события через `Сервис отслеживания РПО` из `Корпоративной шины данных`
  2. **Инкапсуляция чужого контракта:** Вся логика парсинга кодов операций (`ACCEPTING`, `RETURNING_BY_EXPIRED_STORING`) изолирована внутри `Сервиса отслеживания РПО`, который сохраняет исходный код причины для аналитики и отдаёт понятный статус в `BFF`
  3. **Таймауты по умолчанию:** Поскольку внешний контур может не прислать причину отказа в приёме, в воркер заложен жёсткий дедлайн (24 часа), по истечении которого система автоматически разблокирует средства в пользу клиента


## 3. Отсутствие Kafka в контуре кабинета и использование RabbitMQ
* **Суть ограничения:** В контуре личного кабинета брокер Kafka отсутствует (он используется только внутри корпоративной шины, куда кабинет ходит через REST-обвязку). Внутри кабинета работает `RabbitMQ`, который является очередью, а не распределённым логом: после доставки потребителю сообщение удаляется, и перечитать историю событий за прошлый период из брокера невозможно
* **Как обойдено в проекте:**
  1. Аналитический конвейер построен не на прямом чтении брокера, а по пути база -> планировщик: события из `RabbitMQ` сначала фиксируются в операционных/промежуточных таблицах PostgreSQL, откуда планировщик порциями переносит их в аналитическое хранилище. Это позволяет при сбое аналитики перечитать данные из БД
  2. Интеграция с корпоративной шиной вынесена в отдельный асинхронный контейнер `Фоновая публикация в шину`, чтобы медленный ответ внешней REST-обвязки не блокировал потоки основного `REST API`


## 4. Однопоточный пакетный конвейер с жёстким порогом на входе (1000 записей)
* **Суть ограничения:** Существующий механизм массовой загрузки (`Сервис разбора файлов`) не поддерживает разбиение больших файлов на порции и их параллельную обработку - файл разбирается однопоточно и отправляется в `REST API` одним пакетом, из-за чего действует жёсткое ограничение на размер файла в 1000 строк. Построение полноценного распределённого map-reduce конвейера для массовых возвратов потребовало бы переписывания всего ядра загрузки файлов
* **Как обойдено в проекте:**
  1. Массовое оформление возвратов встроено в существующий конвейер с соблюдением границы 1000 строк на файл и валидацией этого лимита до начала парсинга (Уровень 0)
  2. Чтобы снизить трение для клиента при превышении лимита, предусмотрен асинхронный режим с `job_id` и разделение ошибочных строк на неисправимые ("Отклонено") и исправимые (попадающие в интерфейс ручной правки). Асинхронный контракт (`202 Accepted` + поллинг) заранее закладывает точку расширения: при росте объёмов внутреннюю однопоточную обработку можно будет заменить на параллельные воркеры без изменения API для клиентов
