# (в) Организация аналитики для фичи «Управление возвратами»

## 1. Вопросы владельца продукта, на которые отвечает витрина
Проектирование витрины начинается с бизнес-вопросов, требующих агрегации больших объёмов данных без нагрузки на операционные базы PostgreSQL:
1. Какова доля возвратов по каждой причине (истёк срок хранения, отказ получателя, неверный адрес) в разрезе сегментов клиентов за месяц?
2. Какой процент оформленных клиентами возвратов реально доходит до физического приёма в отделении, а какой истекает по таймауту или отменяется?
3. Какова итоговая финансовая нагрузка на клиентов (сумма окончательных списаний за обратную пересылку с учётом корректировок по весу) по каналам оформления (Веб vs API)?


## 2. Тип конвейера загрузки и обоснование

### Архитектура конвейера (на базе реального «Пути Б»)
Сервисы `REST API`, `Сервис отслеживания РПО` и `Онлайн Баланс` публикуют события в `RabbitMQ`. Сервисы-читатели сохраняют данные в промежуточные таблицы, откуда планировщик порциями переносит их в аналитический контур

### Выбор подхода: **ELT** (Extract - Load - Transform)
* **Обоснование выбора:** В систему приходят справочники операций почтовой сети, содержащие около 200 атрибутов. Бизнес-требования к группировке причин возврата меняются (например, сегодня аналитикам нужна общая группа "Неудачное вручение", а завтра - детализация по "Временному отсутствию адресата")
* **Что мы потеряем при ETL:** При классическом ETL (фильтрация и агрегация до загрузки) мы отбросим детальный код `operation_attribute` из справочника операций, заменив его укрупнённым клиентским статусом. Восстановить исходную причину возврата за прошлые месяцы после этого будет невозможно - данные будут потеряны безвозвратно. ELT позволяет сохранять сырые события в хранилище и перестраивать витрины SQL-запросами при изменении правил классификации


## 3. Структура аналитической витрины (`dm_returns`)

### Таблица фактов: `fact_returns`
*Гранулярность:* Одна строка = одна зарегистрированная заявка на возврат отправления

| Поле                      | Тип           | Описание и источник                                                      |
|:--------------------------|:--------------|:-------------------------------------------------------------------------|
| `return_id`               | String / UUID | Уникальный идентификатор заявки на возврат (ключ дедупликации)           |
| `original_rpo_id`         | String        | Идентификатор исходного прямого отправления                              |
| `client_sk`               | Int64         | Суррогатный сквозной ключ клиента (измерение)                            |
| `date_created_key`        | Int32         | Дата оформления возврата (измерение)                                     |
| `channel_key`             | Int16         | Канал оформления: `WEB` или `API` (измерение)                            |
| `reason_code_key`         | String        | Исходный код причины возврата из учётного справочника (измерение)        |
| `final_status`            | String        | Итоговый статус заявки (`Завершена`, `Отклонена`, `Истекла`, `Отменена`) |
| `held_amount`             | Decimal(12,2) | Сумма первоначального удержания (руб)                                    |
| `final_charged_amount`    | Decimal(12,2) | Итоговая списанная сумма с учётом приёма и корректировки по весу (руб)   |
| `processing_duration_sec` | Int32         | Длительность от создания заявки до физического приёма (секунды)          |

### Измерения (Dimensions)
1. **`dim_client` (Клиенты):** Сквозной идентификатор организации, сегмент (КРБ, СМБ и др.), регион. *Обоснование:* Позволяет не путать одного клиента, работающего одновременно через веб и через API
2. **`dim_return_reason` (Причины возврата):** Справочник, связывающий детальный код операции (`RETURNING_BY_EXPIRED_STORING` и др.) с бизнес-группой причины и признаком управляемости (можно ли исправить адрес). *Обоснование:* Обеспечивает прослеживаемость причин без их потери
3. **`dim_channel` (Каналы взаимодействия):** `WEB_SINGLE` (форма), `WEB_BATCH` (файл), `API_SINGLE`, `API_BATCH`. *Обоснование:* Позволяет оценивать нагрузку и долю ошибок по разным входам
4. **`dim_date` (Календарь):** Дата, неделя, месяц, квартал, признак рабочего/выходного дня. *Обоснование:* Необходим для расчёта соблюдения SLA (5 рабочих дней на возврат средств)

### Предвычисленный агрегат: `agg_returns_monthly_summary`
* **Структура:** Группировка по `(month_key, client_sk, reason_code_key, channel_key)` с предвычисленными полями: `total_requests`, `accepted_count`, `rejected_count`, `total_charged_amount`
* **Почему без него не обойтись:** Дашборд руководителя направления и сводные отчёты для крупных клиентов (сегмента КРБ, генерирующего основной объём трафика) строятся за квартал и год по миллионам записей. Без агрегата каждый рендеринг графика вызывал бы полное сканирование таблицы фактов


## 4. Прослеживаемость поля и обработка служебных значений

### Прослеживаемость поля `reason_code_key` (Причина возврата)
1. **Источник (Внешний контур):** Учётная система почтовой сети фиксирует операцию с парой `(operation_type = 'RETURNING', operation_attribute = 'RETURNING_BY_EXPIRED_STORING')` и отправляет в `Корпоративную шину данных`
2. **Приём в ЛК (`Сервис отслеживания РПО`):** Вычитывает событие из шины. *Риск потери смысла:* Если сохранить только маппинг для клиентского UI ("Отправлено обратно отправителю"), детальная причина исчезнет. Поэтому сервис сохраняет оба поля: `ui_status` и `raw_reason_code`
3. **Передача в аналитику (`RabbitMQ` → `ClickHouse`):** Событие `ReturnStatusUpdated` передаёт `raw_reason_code` без преобразований в `fact_returns.reason_code_key`

### Служебные значения и агрегаты
* Если возврат инициирован клиентом до истечения срока хранения (добровольный возврат) или шина прислала событие без атрибута причины, поле `reason_code_key` заполняется служебным значением `UNKNOWN_REASON` (а не `NULL`)
* **Влияние на агрегат:** Использование явного значения `UNKNOWN_REASON` гарантирует, что при группировке (`GROUP BY reason_code_key`) эти записи не выпадут из расчёта общей суммы списаний и доли возвратов, а будут явно видны аналитику как отдельная категория


## 5. Граница актуальности и SQL-запрос к витрине

### Граница актуальности (Eventual Consistency)
Поскольку данные проходят через брокер, планировщик выгрузки и фоновую генерацию `.xlsx`, витрина работает в модели согласованности в конечном счёте
* **Мера в интерфейсе и отчёте:** В каждом выгружаемом `.xlsx` отчёте и на дашборде выводится обязательный заголовок: "Данные актуальны по состоянию на ДД.ММ.ГГГГ ЧЧ:ММ (МСК). Операции, совершённые позднее, будут отражены в следующем цикле обновления". Это исключает восприятие задержки конвейера как потери данных

### Пример SQL-запроса (ответ на вопрос 1 владельца продукта)
```sql
SELECT 
    d.year_month AS period,
    c.segment_name AS client_segment,
    r.reason_group_name AS return_reason,
    COUNT(f.return_id) AS total_returns,
    ROUND(
        COUNT(f.return_id) * 100.0 / SUM(COUNT(f.return_id)) OVER (PARTITION BY d.year_month, c.segment_name), 
        2
    ) AS share_percent
FROM fact_returns f
JOIN dim_date d ON f.date_created_key = d.date_key
JOIN dim_client c ON f.client_sk = c.client_sk
JOIN dim_return_reason r ON f.reason_code_key = r.reason_code_key
WHERE d.year_month = '2026-10'
  AND f.final_status = 'Завершена'
GROUP BY d.year_month, c.segment_name, r.reason_group_name
ORDER BY client_segment, total_returns DESC;
```
