# (г) Ролевая модель - ММСБ

Клиент - организация, субъект - сотрудник или программа. Связь субъекта с выбранным клиентом проверяется при каждом запросе. Роли проектные; в системе известны администратор аккаунта и субаккаунты с лимитами.

| Роль | Уровень | Назначение |
|---|---|---|
| Администратор аккаунта | Администратор | Управляет сотрудниками, интеграциями и лимитами своего клиента, оформляет и контролирует возвраты. |
| Оператор возвратов | Субаккаунт | Оформляет, отменяет, отслеживает возвраты своего субаккаунта в пределах лимита. |
| Бухгалтер | Субаккаунт | Просматривает и выгружает возвраты и операции по балансу; в ММСБ может быть внешним бухгалтером. |
| Интеграция | Субаккаунт программы | Выполняет машинные операции в пределах назначенного лимита. Не использует пароль сотрудника. |

## Матрица: субъект, операция, область видимости

К - объекты своего клиента; С - своего субаккаунта; И - возвраты данной интеграции; Л - проверка баланса и лимита (для администратора только баланса); дефис - запрет. Все области ограничены текущим client_id. Э - экран для сотрудников, П - API для программы. Публичный контракт включает только три метода пункта (а).

| Операция / вход | Администратор | Оператор | Бухгалтер | Интеграция |
|---|---|---|---|---|
| О1 Оформить один, Э | К + Л | С + Л | - | - |
| О1 Оформить один, П (POST /1.0/returns) | - | - | - | С + Л, результат И |
| О2 Оформить списком, Э | К + Л на пакет | С + Л на пакет | - | - |
| О3 Отменить, Э | К | С | - | - |
| О3 Отменить, П (POST /1.0/returns/{returnId}/cancel) | - | - | - | И |
| О4 Перечень, Э | К | С | К | - |
| О4 Перечень, П (GET /1.0/returns) | - | - | - | И |
| О5 Карточка, Э | К | С | К | - |
| О6 Выгрузка, Э | К | С | К | - |
| О7 Удержания, списания, возвраты денег, Э | Операции баланса К | Удержания С | Операции баланса К | - |
| О8 Пользователи, роли, лимиты и ключи, Э | Сотрудники и интеграции К, кроме собственных полномочий | - | - | - |

О2 на экране работает асинхронно (202 + jobId, З-8). Публичные пакетный метод и статус задания пока вне спецификации. О1 и О2 удерживают средства, О3 освобождает удержание, О8 задаёт лимит. Отмена допустима в DRAFT, SUBMITTED до начала регистрации и REGISTERED до приёма; при неопределённой или выполняющейся регистрации - 409 REGISTRATION_IN_PROGRESS.

## Проверка прав

- Шлюз/BFF проверяет подпись, издателя, аудиторию и срок токена (401). Сервер проверяет актуальные права и вход (403). Всё явно не разрешённое запрещено.
- О1: исходное отправление выбирается по barcode, client_id и области субаккаунта; владелец заявки устанавливается сервером. О3: выборка по return_id и client_id, дополнительно subaccount_id для оператора или creator_integration_id для программы; блокировка перед переходом. О4: те же ограничения до фильтрации и пагинации. Чужой ID -> 404. Карточка и выгрузка используют те же области.
- Баланс атомарно проверяет сумму открытых удержаний и новой операции против лимита и доступного остатка; для пакета учитывается общая стоимость. Ошибки LIMIT_EXCEEDED и INSUFFICIENT_FUNDS. Права проверяются на повторе и перед финансовой операцией; начатая операция завершается или сверяется.
- Администратор не повышает собственные права и не обходит запрет второй учётной записью; проверка идентичности, аудит и независимое подтверждение смены администраторов.

Выбор - RBAC для операций + ABAC для области, входа, состояния и лимита. Только RBAC создаёт множество ролей под разные области; только ABAC усложняет обзор полномочий. ACL на каждый возврат избыточны при однотипных объектах. Аудитор добавляется отдельной ролью чтения в назначенной области.

## Проверки против обхода

| Попытка | Ожидаемый исход |
|---|---|
| Оператор подставляет ID другого клиента в карточку или отмену | 404; чтение только внутри client_id и subaccount_id. |
| Бухгалтер напрямую вызывает POST отмены | 403; проверка входа и операции на сервере. |
| Интеграция читает/отменяет возврат другой интеграции того же клиента | Не попадает в перечень / 404. |
| Администратор меняет собственные права через API или новый аккаунт | Запрещено; проверка полномочий и идентичности. |
| Два параллельных оформления превышают лимит | Одно отклоняется атомарной проверкой баланса. |
| Токен действует после отзыва разрешения | 403 при актуальной проверке прав. |

## Аудит и подпись

Для оформления (включая пакет) и отмены: subject_id, client_id, subaccount_id, операция, вход, returnId или ID пакета/строки, время сервера, результат и причина, traceId, ссылка на ключ, сумма, причина возврата, состояния до/после. Для интеграции сохраняется выдавший доступ субъект. При приёме и сверке - ШПИ, тип финансовой операции, ключ и результат. Пароли и токены не журналируются. Это позволяет разобрать споры о расходах и отмене. УКЭП не требуется: операции идут в рамках договора; подпись каждой строки непрактична для ММСБ (учебное решение).
