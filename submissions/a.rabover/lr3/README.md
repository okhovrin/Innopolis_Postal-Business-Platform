# (а) Интеграционная карта

## Согласование модели состояний З-6, З-7, З-8 и З-10

| З-6 | Публичное состояние в ЛР-3 | Смысл |
|---|---|---|
| Черновик | DRAFT | До подтверждённого удержания |
| Ожидает ШПИ | SUBMITTED (Оформлена) | Удержание подтверждено, регистрация отложена |
| Выдан покупателю | REGISTERED (Зарегистрирована) | ШПИ присвоен; доставка уведомления учитывается отдельно |
| Принят в отделении | IN_TRANSIT (В пути) | Точка невозврата, начинается окончательное списание |
| Получен организацией | DELIVERED | Вручён организации |
| Аннулирован | CANCELLED | Отменён |
| Не выпущен | REJECTED | Регистрация завершилась отказом |
| Просрочен | EXPIRED | Срок сдачи истёк |
| Завершён без получения | CLOSED_UNDELIVERED | Закрыт без вручения |

В З-6 был отдельный статус «Требует исправления» с пределом 3 попытки / 7 дней. В более позднем З-8 постоянный отказ регистрации ведёт к REJECTED, а исправляемые ошибки файла относятся к результату строки задания. Для ЛР-3 выбран этот более поздний вариант; цикл исправления уже зарегистрированной заявки в трёх публичных методах отсутствует. Для новой исправленной заявки нужна новая команда.

З-6 запрещал отмену в ожидании ШПИ, З-7 и З-10 допускают отмену оформленной заявки. Сохраняем возможность из З-10 только для ещё не начатой регистрации: сервис атомарно отменяет ожидающую задачу; при начатой регистрации или неопределённом результате возвращает 409 REGISTRATION_IN_PROGRESS с currentState, после завершения регистрации клиент проверяет состояние. Так воркер и отмена не могут независимо зарегистрировать и отменить одну заявку. Для REGISTERED требуется подтверждение снятия регистрации от почтовой сети до освобождения удержания. После IN_TRANSIT отмена запрещена.
# Что изменилось относительно черновиков

| Источник / расхождение | Решение и почему |
|---|---|
| З-6-8: разные названия состояний, правила отмены и фоновой регистрации | Сохранена терминология З-7/8/10; добавлены явное соответствие З-6, защита от гонки отмены с воркером, причина возврата, финансовый статус и возраст данных. |
| З-10 описывал только отмену | Добавлены ресурсные POST и GET /1.0/returns; процедурная отмена и её состояния сохранены. Создание 201, чтение 200. |
| З-10: 500/503 «состояние не изменено» | При распределённых эффектах это не гарантируется: сохранённый результат не подтверждается до сверки, промежуточный эффект мог произойти. Повтор идемпотентен. |
| З-10: необязательный ключ | Для оформления с деньгами ключ обязателен; для отмены рекомендован, защищён и переходом состояния, и устойчивым ключом освобождения. |
| З-10 не описывал 403 | Добавлен по матрице З-12; чужая заявка - 404, отсутствие разрешения - 403. |
| З-11 фиктивный CREATED против состояний З-10 | CREATED - внутренний результат мока, публичный 201 содержит SUBMITTED. 502/504/503 CIRCUIT_OPEN отражены в YAML и документации оформления. |
| З-13 помещал размыкатель на уведомления, З-11 - на оформление | Выбрано направление З-11, потому что уже реализован и проверен именно этот вызов и ошибка должна быть видна интегратору. Добавлена связь 7. Альтернатива - размыкатель уведомлений, тогда ошибка отправки письма видна воркеру. Клиент оформления не получает 503 из-за письма. |
| З-12: восемь операций, часть с обоими входами | В матрице оставлены все операции, но явно ограничена текущая публикация тремя методами. Экран и перспективный API не смешиваются с доступным контрактом. |
| З-12: интеграция как отдельная запись, в реальной схеме её наличие неизвестно | Учебный Bearer / Client Credentials, ограниченный субаккаунт. Реальные секреты не выдуманы; отличие от токена приложения и ключа пользователя раскрыто в документации. |
| З-13: события для разных сегментов | Все клиентские сценарии адаптированы для ММСБ; уведомления не блокируют оформление. |
| З-11: базовые тесты и дополнительные улучшения | Сохранён полный вариант, демонстрация и тесты извлечены из предоставленных файлов; параметры демонстрации отделены от предлагаемых рабочих. |
