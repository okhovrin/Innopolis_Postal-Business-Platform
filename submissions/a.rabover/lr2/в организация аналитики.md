# Структура витрины

**Один факт — это:** одна оформленная заявка на возврат (одна строка таблицы фактов fact_return соответствует одной заявке, перешедшей из «Черновик» в «Оформлена»)
**Числовые показатели факта:** стоимость возврата, руб., часов от оформления до регистрации, дней от регистрации до приема в отделении, дней от приема до вручения.

| **Измерение (не менее четырёх)** | **Зачем: какое решение вы примете, увидев разрез по нему**                                                           | **Откуда берётся ключ**                                                     |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Период (дата оформления)         | Видна сезонность и рост после релизов. Решаем, связан ли рост потерь с изменением в продукте или с сезоном распродаж | Дата из события перехода «Черновик» -> «Оформлена», ключ из справочника дат |
| Клиент (с атрибутом «сегмент»)   | Кто из клиентов дает аномально много возвратов – персональная работа менеджера                                       | Сквозной идентификатор юрлица (ИНН + КПП)                                   |
| Причина возврата                 | Какие причины предотвращать на стороне создания отправления                                                          | Код из справочника причин, который клиент выбирает в «Черновик»             |
| Исход                            | На каком шаге теряются заявки                                                                                        | Состояние «Вручена/Отклонена/Истекла/Закрыта без вручения»                  |
| Регион (ОПС приема)              | Где логистика медленнее нормы – претензии и перераспределение                                                        | Индекс ОПС из события почтовой сети «возврат принят в отделении»            |

**Агрегат:** месяц оформления $\times$ сегмент $\times$ причина $\times$ исход. Число заявок, сумма стоимости, сумма дней в пути и число заявок с известной длительностью

**Почему без него не обойтись:** вопросы 1 и 3 задаются каждый месяц, и без агрегата каждый отчет заново сканирует все факты. Хранение суммы и счетчика вместо среднего позволяет правильно сворачивать агрегат дальше.
# Прослеживаемость одного поля
**Поле витрины:** fact_return.delivered_at – момент вручения возврата отправителю

| **Шаг**                          | **Где живёт поле (событие / таблица / поле витрины)** | **Как называется здесь** | **Что с ним делается**                                                                     | **Может ли здесь измениться смысл**                            |
| -------------------------------- | ----------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| Порождающее событие (модель З-6) | Переход «В пути – Вручена отправителю»                | occurred_at              | Берется из статуса почтовой сети, кладется в событие вместе с event_id и state = DELIVERED | Да, если подставить время когда фоновая задача заметила статус |
| Таблица сервиса-читателя         | return_state_history в базе сервиса возвратов         | changed_at               | Читатель пишет строку истории                                                              | Да, если читатель пишет now() вместо occurred_at               |
| Сырой слой хранилища (ELT)       | raw_return_events в аналитической базе                | event_ts                 | Копируется без преобразования, в UTC                                                       | Нет, если не преобразовывать                                   |
| Витрина                          | fact_return                                           | delivered_at             | Берется event_ts события DELIVERED по заявке, переносится в МСК для отчета                 | Да, смешение форматов времени сдвигает даты на границе суток   |
# SQL-запрос к витрине

```sql
SELECT

    d.month_start AS month,
    COUNT(*) AS submitted,
    COUNT(*) FILTER (WHERE f.outcome = 'DELIVERED') AS delivered,
    COUNT(*) FILTER (WHERE f.outcome = 'CANCELLED') AS cancelled, -- отменил клиент
COUNT(*) FILTER (WHERE f.outcome = 'REJECTED') AS rejected, -- не зарегистрирована
    COUNT(*) FILTER (WHERE f.outcome = 'EXPIRED') AS expired, -- не сдана за 14 дней
    COUNT(*) FILTER (WHERE f.outcome = 'CLOSED') AS closed, -- без вручения
    COUNT(*) FILTER (WHERE f.outcome IS NULL) AS in_progress, -- исход еще неизвестен
    ROUND(100.0* COUNT(*)  
FILTER (WHERE f.outcome IN ('CANCELLED','REJECTED','EXPIRED','CLOSED')) / NULLIF(COUNT(*)  
FILTER (WHERE f.outcome IS NOT NULL), 0), 1) AS lost_pct, -- от заявок с известным исходом
    MAX(f.loaded_at) AS data_as_of -- граница актуальности
FROM fact_return AS f
JOIN dim_date AS d ON d.date_key = f.submitted_date_key
WHERE d.month_start >= DATE_TRUNC('month', CURRENT_DATE) - INTERVAL '5 months'
GROUP BY d.month_start
ORDER BY d.month_start;
```
# Что уточнено относительно черновика З-9 при сборке

- Регион
  Индекс ОПС берётся из события приёма, но в событии приёма З-7 есть только ШПИ и вес, а в модели З-6 не было индекса. Добавила индекс в то, что трекер читает по ШПИ и сохраняет в `return_state_history`
- "Стоимость возврата" в З-9 был один показатель, а в З-7 две суммы (удержано S и списано S +- разница по весу). Для вопроса 3 верна вторая. Показатель разделён на `cost_held` и `cost_charged`
- `occurred_at` и `recorded_at`. Риск подмены `now()` закрыт двумя полями в истории
