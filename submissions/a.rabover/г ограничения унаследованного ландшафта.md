# Ограничение 1, главное. Статус отправления приходит из корпоративной шины через REST-обвязку

Сервис отслеживания РПО читает операции почтовой сети из корпоративной шины через REST-обвязку. Кабинет не владеет учетной системой почтовой сети. В источниках не указано, чем возвратная операция отличается от обычной.
Что сломается, если обвязка не отдает нужное:

| Часть решения                                          | Что нужно из шины                           | Что сломается                                                                                  |
| ------------------------------------------------------ | ------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Переходы "Зарегистрирована - В пути - Вручена/Закрыта" | операция по ШПИ возврата                    | Заявка навсегда остается "Зарегистрированной", удержание повисает до сверки ("старше 15 дней") |
| Окончательное списание                                 | ШПИ для ключа `ШПИ + "списание при приеме"` | Ключ не собрать, списания нет                                                                  |
| +- Разница по весу                                     | вес при приеме                              | Разница не считается                                                                           |
| Регион в витрине                                       | индекс ОПС приема                           | На вопрос 2 нельзя ответить                                                                    |
| `delivered_at` в витрине                               | время операции                              | Остается время, когда трекер заметил статус                                                    |

## Как обходить
1. Кабинет заранее знает ШПИ возврата, его выдает API отправлений. Трекер спрашивает статус по этому ШПИ, поэтому отличать возвратную операцию от обычной не нужно.
2. Сохранять все сырым при первом чтении (время, вес, ОПС в `return_state_history`).
3. Не подменять отсутствующие данные догадкой. Например, нет веса - списание по S с пометкой "вес не передан".
4. Минимальное изменение ландшафта -попросить владельца REST-обвязки отдавать время, вес и ОПС вместе со статусом.

Цена обхода
Возвраты, которые инициировала сама почтовая сеть без заявки клиента, не входят в фичу, связать их с клиентом не по чему.

# Ограничение 2. Нет единого бэкенда, методы смежных сервисов меняет только команда-владелец
В организации нет единого языка и единого бэкенда, поэтому каждый новый метод в API отправлений или Онлайн Балансе это работа другой команды в ее очереди приоритетов. Решению нужны три операции, которых может не быть: регистрация одиночного встречного отправления, отмена по требованию отправителя и удержание вне формирования партии.

## Как обходить
Возврат - встречное отправление с переставленными ролями, поэтому его можно регистрировать существующим методом создания отправления и удерживать через партию из одного отправления. Цена - служебные партии придется скрывать фильтром. Все обращения к смежникам идут через один фасад в сервисе возвратов, чтобы при появлении нормального метода поменять одно место.

# Ограничение 3. Удержание может быть доступно только как "запрос-ответ через очередь"
Синхронизация баланса сделана как RPC поверх RabbitMQ. Если удержание есть только в такой форме, не будет синхронного ответа для перехода "Черновик - Оформлена".

## Как обходить
Добавляю состояние "Ожидает удержания" между "Черновиком" и "Оформлена". Его продвигает воркер по ответу из очереди, дедлайн 1ч (допущение), после него заявка возвращается в "Черновик". Цена - клиент ждет ответа на "оформить" до следующего цикла воркера.
