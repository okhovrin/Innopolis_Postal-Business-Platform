# (г) Ограничения унаследованного ландшафта

[← к оглавлению](README.md)

Черновика нет — пункт написан при сборке. Ограничения взяты из состава системы, разобранного на занятии 5 и отражённого на [схеме контейнеров](0-decomposition.md#2-диаграмма-контейнеров-c4): каждое привязано к конкретному существующему контейнеру и конкретному решению этой работы, которое оно делает недостижимым.

## Сводка

| № | Ограничение ландшафта | Какое решение оно ломает | Обход |
|---|---|---|---|
| 1 | Онлайн Баланс общается с кабинетом только через RabbitMQ в режиме RPC и синхронизирует состояние с системой финансового учёта | Удержание до создания РПО с ключом идемпотентности и запросом статуса по ключу | Адаптер в сервисе возвратов + сверка; при отсутствии удержания — изменение порядка операций |
| 2 | Статусы почтовой сети попадают в кабинет только опросом: трекинг читает операции из корпоративной шины по REST | Точка невозврата, привязанная к подтверждённому приёму | Неограниченное ожидание в `AwaitAccept` и сверка вместо таймера |
| 3 | REST API — единственная точка создания отправлений, со своей базой; у отправления нет связи «исходное ↔ встречное» и поиска по внешнему ключу | Безопасный повтор «создать или найти» встречное РПО | Поле связи в REST API; до его появления — поиск по исходному РПО и `ManualReview` при неоднозначности |
| 4 | Сервис разбора файлов имеет предел на файл (граница на входе) | Оформление любого числа возвратов одним файлом | Принять предел, сообщить его заранее, основным каналом для больших объёмов сделать API |

## 1. Онлайн Баланс: нет удержания по внешнему ключу

**Ограничение.** Онлайн Баланс — существующий сервис, который обменивается с кабинетом сообщениями RabbitMQ в режиме RPC, а остатками и проводками — с системой финансового учёта. Работа опирается на три его возможности: (а) отдельная операция «удержать», а не только «списать»; (б) приём ключа идемпотентности от вызывающего; (в) запрос статуса операции по этому ключу.

**Почему решение становится недостижимым.** Если хотя бы (б) или (в) нет, то при таймауте в `HoldPending` невозможно узнать, удержаны ли деньги. Повтор может удержать дважды, отказ от повтора — оставить деньги удержанными без заявки. Вся машина состояний строится на том, что исход «неизвестно» рано или поздно становится известным; без запроса по ключу он становится известным только при ручной сверке с системой финансового учёта — то есть каждая потеря ответа превращается в `ManualReview`. Если нет (а), то нет и удержания — только окончательное списание, и порядок «удержать → создать РПО → списать после приёма» невозможен.

**Обход.**

- Если нет (б) и (в): **адаптер в сервисе возвратов**. Перед вызовом записываем операцию в `operations` с нашим ключом и передаём ключ в поле назначения платежа (комментарии/метаданных), которое баланс уже хранит и возвращает в выписке. Статус ищем по выписке за интервал вызова. Неоднозначность → `ManualReview`. Это медленнее, но не создаёт двойных удержаний.
- Если нет (а): **меняем порядок**. Сначала создаём встречное РПО (обратимо до приёма), а списываем один раз после приёма — без удержания. Цена решения — риск, что у клиента к моменту приёма не хватит денег на балансе; это фиксируется в договоре (приём с последующей задолженностью) и становится отдельным исходом в модели.
- Долгосрочно — доработка баланса (операции с ключом) как условие фичи; это изменение унаследованного сервиса, его стоит планировать заранее (ЛР-4, план замещения).

## 2. Статусы почтовой сети приходят только опросом

**Ограничение.** Почтовая сеть не сообщает кабинету о событиях напрямую: трекинг сам опрашивает операции в корпоративной шине данных по REST и передаёт историю в REST API. Задержка между приёмом посылки в отделении и появлением статуса в кабинете не ограничена сверху и порядок операций не гарантирован.

**Почему решение становится недостижимым** в варианте «списать по таймеру». Если бы точка невозврата была привязана ко времени («через N часов после создания РПО считаем, что посылку приняли»), задержка опроса приводила бы к списанию за непринятые посылки или к отмене уже принятых.

**Обход.** Он уже заложен в модель: `AwaitAccept` не имеет таймера на списание, переход выполняется только после проверки приёма по `acceptance_id`, сигнал из очереди — лишь повод проверить ([пункт (б), п. 6](b-states.md#6-событийные-уведомления--не-переходы)). Клиент видит последний известный статус и его время. Для заявок, которые слишком долго в `AwaitAccept`, оператор получает отчёт, но заявка сама не двигается.

## 3. REST API не умеет «создать или найти» встречное РПО

**Ограничение.** Отправления создаёт только REST API, у него своя база (принцип «база на сервис»), и сервис возвратов не может читать её напрямую. В текущей модели отправления нет поля «исходное РПО» и нет поиска по ключу вызывающей стороны.

**Почему решение становится недостижимым.** Повтор после таймаута в `CreatePending` без поиска по ключу создаёт второе встречное РПО — две посылки, два адреса возврата, путаница со списанием. Без связи «исходное ↔ встречное» нельзя проверить, что по одному исходному РПО уже оформлен возврат.

**Обход.**

- Доработка REST API (она уже указана в декомпозиции): поле связи с исходным РПО и уникальный ключ создания `reverse:<return_id>`.
- Пока доработки нет: перед повтором сервис возвратов ищет отправления клиента по исходному РПО и интервалу времени через существующие методы чтения REST API. Одно найденное — берём его; ни одного — повторяем; больше одного — `ManualReview`.

## 4. Граница на входе сервиса разбора файлов

**Ограничение.** Сервис разбора файлов принимает файл ограниченного размера (в работе принято 1000 строк — **учебное допущение**). Это свойство существующего сервиса, а не фичи.

**Почему это ограничение.** Клиент, которому нужно оформить больше возвратов, не может сделать это одной загрузкой и одним отчётом.

**Обход.** Предел не обходится, а принимается: клиент узнаёт о нём до загрузки, делит файл и сверяет несколько отчётов ([пункт (а), п. 4](a-architecture.md#4-конвейер-массового-оформления-возвратов)). Для больших объёмов основным каналом объявляется API с пакетными вызовами.

## Что из этого критично

Ограничения 1 и 3 делают решение **недостижимым** без доработки унаследованных сервисов: без них нельзя гарантировать отсутствие двойного удержания и двойного РПО. Ограничения 2 и 4 решение **переживает**: они определяют, как устроено ожидание и вход, но не ломают модель.
