# (в) Организация аналитики

[← к оглавлению](README.md)

Черновик: З-9. Витрина проектируется от вопросов: сначала — что нужно узнать, потом — что для этого хранить.

## Вопросы владельца продукта

| № | Вопрос | Какое решение он поддерживает |
|---|---|---|
| 1 | Какая доля заявок дошла до оформленного встречного РПО — по каналам и дням регистрации? | Найти канал и этап, где теряются заявки; приоритет диагностики. |
| 2 | Сколько заявок застряло в финансовой неопределённости (`HoldPending`, `DebitPending`, `ReleasePending`, `ManualReview`) и сколько она длится? | Настроить сверку с балансом и приоритет ручного разбора. |
| 3 | По каким причинам и у каких клиентов возвраты отклоняются или отменяются чаще всего — **включая строки файлов, отсеянные до создания заявки**? | Уточнить проверки, справочник причин, подсказки интерфейса и описание формата файла. |

## 1. Состав данных

Источник — уведомления сервиса возвратов и сервиса разбора файлов ([пункт (б), п. 6](b-states.md#6-событийные-уведомления--не-переходы)). Ни один показатель не берётся из чтения рабочей базы сервиса напрямую.

| Уведомление | Поля | Какие показатели витрины порождает |
|---|---|---|
| `return_registered` | `event_id`, `return_id`, `client_id`, `channel` (web / api / file), `job_id`, `reason_code`, `occurred_at` | `registered_at`, канал, клиент, причина |
| `return_rejected` | `return_id`, `error_code`, `occurred_at` | `final_error_code`, признак отказа |
| `hold_confirmed` | `return_id`, `amount`, `occurred_at` | `hold_amount`, `hold_confirmed_at` |
| `reverse_shipment_confirmed` | `return_id`, `reverse_rpo_id`, `occurred_at` | `reverse_created_at` |
| `acceptance_confirmed` | `return_id`, `acceptance_id`, `weight`, `occurred_at` | `accepted_at` |
| `return_settled` | `return_id`, `final_price`, `settled_amount`, `occurred_at` | `final_price`, `settled_amount`, `settled_at` |
| `return_closed` | `return_id`, `close_reason` (cancelled / expired), `occurred_at` | `closed_at`, причина закрытия |
| `return_manual_review` | `return_id`, `from_state`, `occurred_at` | `manual_review_at`, `manual_review_from` |
| `job_row_rejected` (сервис разбора файлов) | `job_id`, `row_key`, `client_id`, `level` (1 / 2), `error_code`, `occurred_at` | факт строки файла без заявки (вопрос 3) |

Справочники: клиент и сегмент (договорный справочник), календарь, справочник причин.

## 2. Тип конвейера загрузки

**ELT с микропакетной загрузкой.** Уведомления идут из RabbitMQ через фоновую публикацию в корпоративную шину, оттуда **без преобразований** — в сырой слой аналитического хранилища; преобразования выполняются уже в хранилище.

| Альтернатива | Почему не выбрана |
|---|---|
| **ETL** (преобразовать до загрузки) | Уведомления приходят с повторами и задержками, а финансовая сверка может изменить вывод задним числом. При ETL ранняя нормализация теряет исходные `reason_code`, `event_id` и время события — их нельзя восстановить, и перепроверить итог сверки нельзя. Конкретное поле, которое рискуем потерять: исходный `reason_code` (до приведения к справочнику) и связь с транзакцией баланса. |
| **Потоковая обработка** (витрина обновляется по каждому событию) | Вопросы 1–3 задаются по дням, а не по секундам; потоковая витрина усложняет дедупликацию и поздние события, не давая владельцу продукта нового решения. Оперативный контроль зависших заявок делает не витрина, а воркер и оповещения ([пункт (а)](a-architecture.md#5-обнаружение-расхождений)). |
| **Чтение рабочей базы returns-db** | Нагружает рабочую базу и связывает аналитику со схемой сервиса; при изменении схемы витрина ломается. Уведомления — стабильный контракт. |

Слои:

1. **raw** — уведомления как пришли: `event_id`, `event_type`, `payload`, `occurred_at`, `ingested_at`.
2. **staging** — дедупликация по `event_id`, разбор полей, связь по `return_id`; при повторе берётся первое подтверждённое время.
3. **mart** — витрины ниже, пересчитываются микропакетом раз в час (допущение).

## 3. Структура витрины

### `fact_returns` — один факт = одна заявка (`return_id`)

Не клиент и не повтор запроса. Строка обновляется по мере прихода уведомлений.

| Измерение | Какое решение принимаем по разрезу | Откуда ключ |
|---|---|---|
| Дата регистрации (когорта) | Отличить проблему новых заявок от старых, сравнить периоды | `registered_at` из `return_registered`; календарь |
| Клиент, сегмент | Найти клиентов с систематическими задержками и сверить баланс | `client_id` из `return_registered`; договорный справочник — ключ связи с балансом и финансовым учётом |
| Канал (web / api / file) | Понять, где больше ошибок интеграции | `channel` из `return_registered` |
| Причина возврата / код отказа | Улучшить проверки и подсказки | `reason_code`, `final_error_code`; исходное значение хранится в raw |
| Текущее состояние | Выделить финансовую неопределённость | последнее уведомление по заявке |

| Показатель | Смысл | Если неизвестно |
|---|---|---|
| `hold_amount` | удержанная сумма | `NULL` |
| `final_price`, `settled_amount` | итоговая цена и списанная сумма | `NULL` до `return_settled` |
| `reverse_created_at` | момент подтверждённого создания встречного РПО | `NULL` |
| `time_to_reverse_s` | `reverse_created_at - registered_at` | `NULL` |
| `uncertainty_s` | время в `HoldPending` / `DebitPending` / `ReleasePending` / `ManualReview` | считается по уведомлениям; открытый интервал — до `data_as_of` |
| `source_watermark_at` | до какого момента загружены уведомления по этой заявке | — |

### `fact_job_rows` — один факт = одна строка файла (`job_id` + `row_key`)

Нужна для вопроса 3: строки, отсеянные на уровне 1, не получают `return_id` и в `fact_returns` не попадают. Измерения: дата задания, клиент, уровень проверки, код ошибки.

## 4. Агрегаты для отчёта

| Агрегат | Зерно | Показатели | Вопрос |
|---|---|---|---|
| `agg_returns_daily` | день регистрации × сегмент × канал | `registered_count`, `created_count`, `created_pct`, `rejected_count`, `uncertain_count`, `manual_review_count` | 1, 2 |
| `agg_uncertainty` | день × состояние неопределённости | число заявок, медиана и 95-й перцентиль `uncertainty_s`, доля дольше 30 минут | 2 |
| `agg_rejections` | неделя × сегмент × источник (заявка / строка файла) × код | число отказов, доля от всех попыток | 3 |

Запрос к витрине — ответ на вопрос 1:

```sql
SELECT date_trunc('day', registered_at)::date            AS day,
       segment,
       channel,
       count(*)                                           AS registered_count,
       count(*) FILTER (WHERE reverse_created_at IS NOT NULL) AS created_count,
       round(100.0 * count(*) FILTER (WHERE reverse_created_at IS NOT NULL)
             / nullif(count(*), 0), 2)                    AS created_pct,
       count(*) FILTER (WHERE current_state IN
             ('HoldPending', 'DebitPending', 'ReleasePending', 'ManualReview')) AS uncertain_count,
       min(source_watermark_at)                           AS data_as_of
FROM fact_returns
GROUP BY 1, 2, 3
ORDER BY 1, 2, 3;
```

## 5. Значение «неизвестно»

`final_price`, `settled_amount`, `reverse_created_at` = `NULL` означает «итог ещё неизвестен». `SUM` игнорирует `NULL`, поэтому рядом всегда выводится число заявок с неизвестным итогом. Неизвестная сумма никогда не заменяется нулём, а заявка в `HoldPending` не считается потерянной.

## 6. Граница актуальности

В отчёте явно: «Данные по состоянию на <`data_as_of`>» и «Отчёт сформирован <время>». `data_as_of` — минимум подтверждённых времён загрузки всех нужных источников, а не время открытия страницы. Пример (учебный): «по состоянию на 04.11.2026 12:00 UTC, сформирован 12:05 UTC». При отказе фоновой публикации или шины ([пункт (а)](a-architecture.md#что-будет-с-фичей-при-отказе-каждой-системы)) отметка перестаёт сдвигаться — это видно в отчёте.

## 7. Прослеживаемость одного поля

`reverse_created_at`:

| Шаг | Где | Имя | Что делается | Может ли измениться смысл |
|---|---|---|---|---|
| Переход | returns-db | `CreatePending → AwaitAccept` | Запись подтверждения от REST API | — |
| Уведомление | outbox → RabbitMQ | `reverse_shipment_confirmed.occurred_at` | Время подтверждения, не время отправки | Нет, если время берётся у подтверждающего источника |
| raw | хранилище | `occurred_at`, `ingested_at`, `event_id` | Загрузка как есть | Да, если подменить `occurred_at` на `ingested_at` |
| staging | хранилище | `first_confirmed_reverse_at` | Дедупликация по `event_id` | Да, если повтор принять за новое РПО |
| mart | `fact_returns` | `reverse_created_at` | Подтверждённое время или `NULL` | Нет при сохранении raw и ключей |
